# Test Plan — AF-202 Implement GitHub MCP read tools

> 配套 `docs/design-notes/AF-202.md`。状态：**Approved v2 / Executed for Human Review**。共享契约 §0A 的 v2 测试要求具有优先级。

## Scope

验证四个只读工具的 Schema、分页边界、Timeout、七类错误映射。全程 mock HTTP 层（`respx`/`httpx.MockTransport` 或等价机制,由 Codex 选定),不连接真实 GitHub。

## Draft v2 mandatory tests

- 多页 tree 返回 `RepositoryTree.entries` 和正确 `truncated`，不得丢失截断信号。
- `find_pull_request_by_head_or_marker()` 覆盖无命中、唯一命中和冲突多命中，且 GitHub 写调用为 0。
- 所有异步 timeout/rate-limit/malformed-response 映射稳定，日志不含 token。

## 测试先行顺序

1. 四个工具各自的正常路径。
2. 分页边界（`max_items` 生效)。
3. 七类错误映射逐一触发。
4. Timeout 测试。
5. 模块边界测试。

## Unit / Component Tests

| 测试 | 断言要点 |
|---|---|
| `test_read_repository_tree_returns_entries` | mock 分页响应,断言合并后的 `TreeEntry` 列表完整、顺序保留 |
| `test_read_repository_tree_respects_max_items` | mock 超过 `max_items` 的数据量,断言列表长度封顶且不再翻页请求 |
| `test_read_file_content_decodes_utf8` | mock base64 编码响应,断言正确解码 |
| `test_read_file_content_binary_marks_truncated` | mock 二进制/不可解码内容,断言 `content=""`, `truncated=True`,不抛异常 |
| `test_read_issue_maps_fields` | mock Issue 响应,断言字段一一映射 |
| `test_read_pull_request_diff_aggregates_files` | mock 多文件 Diff 响应,断言 `files` 完整、`additions`/`deletions` 正确 |
| `test_maps_404_to_not_found` | mock 404 → `GitHubResourceNotFoundError` |
| `test_maps_403_to_permission_denied` | mock 403（非 rate limit）→ `GitHubPermissionDeniedError` |
| `test_maps_rate_limit_to_retryable_error` | mock 429 或 403+`X-RateLimit-Remaining: 0` → `GitHubRateLimitedError`,`retry_after` 从响应头正确换算 |
| `test_maps_5xx_to_upstream_error` | mock 500/502/503 → `GitHubUpstreamError` |
| `test_maps_timeout_to_timeout_error` | mock 超时（`timeout_seconds` 极小值 + 延迟响应）→ `GitHubTimeoutError` |
| `test_maps_malformed_json_to_malformed_response_error` | mock 非 JSON 或缺字段响应 → `GitHubMalformedResponseError` |
| `test_all_error_types_do_not_leak_raw_http_exception` | 断言所有映射异常的类型都在 SHARED-CONTRACTS §5.3 的七类枚举内,调用方不会看到底层 HTTP 库的异常类型 |
| `test_client_reuses_installation_token_provider` | mock `InstallationTokenProvider.get_token`,断言多次工具调用复用同一 Provider（不绕过 AF-201 的缓存逻辑） |

## Component / Integration / Fault Injection

**Component（mock HTTP 级）**：见上表。**Integration**：不适用（无真实 GitHub 连接，见 Limitations）。**Fault Injection**：429/5xx/timeout 已在上表覆盖，对齐 `08_TEST_STRATEGY.md` Fault Injection 清单里的 "GitHub 429/5xx"。

## 模块导入边界测试

`gateway/github/read_tools.py` 允许导入 GitHub REST 客户端库；`packs/delivery/*` 不允许直接导入该库（只能通过工具函数接口调用）。

## Negative / Security Tests

- Token 值不出现在任何请求日志断言输出中（复用 AF-201 的脱敏纪律）。
- `max_items` 为 0 或负数时拒绝（`ValueError`），不静默当作"无限制"处理。
- 路径参数包含 `../` 等穿越模式时按字面值传给 GitHub API（GitHub 自身会 404，不在客户端层做额外路径穿越防护——因为这不是本地文件系统访问,不同于 AF-106 的 root 注入场景；测试断言这类输入不会导致本地文件系统访问）。

```bash
uv run --locked python -m pytest tests/gateway/github/test_read_tools.py -v
uv run --locked python -m pytest -v
```

## 失败判定

- 任一错误类型映射错误或泄露底层异常类型。
- 分页未正确封顶或无限翻页。
- Token 值出现在任何可观测输出中。
- 测试套件触发真实网络请求。

## 本 Issue 不测试的未来能力

真实 GitHub API E2E 留给 AF-210 的受保护手动冒烟；Policy Gate 与 Idempotency Ledger 不适用于纯读调用。

## Evidence

本地 PostgreSQL 16（Alembic head）执行完整套件：`283 passed`；总覆盖率 `91.91%`，高于 90% 门槛。AF-202 针对性测试覆盖分页/截断、UTF-8 与二进制文件、Issue、PR Diff、远端 PR reconciliation、权限/限流/5xx/timeout/malformed 映射、Secret 不记录和只读 HTTP 方法。

## Limitations

全部测试基于 mock HTTP 响应；GitHub 真实 API 的分页 Header 格式、Rate Limit Header 精确命名等,只有在 AF-210 使用真实测试仓库时才会被首次验证,存在"mock 假设与真实行为不一致"的残余风险,需在 AF-210 阶段专门确认。
