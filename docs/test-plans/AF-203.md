# Test Plan — AF-203 Implement repository knowledge ingestion

> 配套 `docs/design-notes/AF-203.md`。状态：**Draft v2**，等待人工最终 Review。共享契约 §0A 的 v2 测试要求具有优先级。

## Scope

验证分块、确定性 Embedder、增量索引管道（幂等/变化检测/越界清理）、迁移 up/down/reapply、`PgVectorContextRetriever` 的租户/仓库隔离与基本检索正确性。需要 CI 的 PostgreSQL（`pgvector/pgvector:pg16`）服务容器。不评测语义排序质量。

## Draft v2 mandatory tests

- 分块在行数/字符数边界保留准确 `start_line/end_line`，检索结果调用现有 `retrieve()` 并生成可验证 Citation。
- 相同请求在不同 tenant/repository 注入下不能跨边界命中。
- 疑似 Secret chunk 被隔离或跳过，原始内容和脱敏内容均不进入检索结果。
- 使用官方 pgvector 类型完成 migration upgrade/downgrade 与索引查询。

## 测试先行顺序

1. `chunk_text` 边界测试（行数/字符数切界)。
2. `DeterministicHashEmbedder` 确定性与零文本测试。
3. 迁移 up/down/reapply（本地 PostgreSQL）。
4. `ingest_file` 幂等/变化检测/越界清理。
5. `PgVectorContextRetriever` 隔离与基本检索。

## Unit / Component Tests

| 测试 | 断言要点 |
|---|---|
| `test_chunk_text_splits_by_max_lines` | 超过 `max_lines` 的文本在行边界处切开 |
| `test_chunk_text_splits_by_max_chars` | 单行超长文本按字符数切开 |
| `test_chunk_text_empty_input_returns_empty_list` | 空文本 → `[]` |
| `test_embedder_is_deterministic` | 同一文本两次 `embed()` 返回完全相同的向量 |
| `test_embedder_similar_text_closer_than_dissimilar` | 高重叠文本对的 cosine 距离显著小于不相关文本对（验证词袋哈希具备基本局部性,不是纯随机） |
| `test_embedder_empty_text_returns_zero_vector_without_error` | 空字符串 → 全零向量,不抛异常 |
| `test_migration_0003_upgrade_creates_extension_and_table` | `alembic upgrade` 后 `pg_extension` 含 `vector`,`repository_chunks` 表存在且列类型正确 |
| `test_migration_0003_downgrade_drops_table_keeps_extension` | `alembic downgrade` 后表消失,`vector` 扩展仍存在 |
| `test_migration_0003_reapply_is_idempotent` | upgrade→downgrade→upgrade 不报错 |
| `test_ingest_file_first_run_writes_all_chunks` | 首次 ingest → `changed == len(chunks)`, `skipped == 0` |
| `test_ingest_file_unchanged_content_skips_all` | 相同内容二次 ingest → `changed == 0`, `skipped == len(chunks)`,数据库无新写入（用 `updated_at` 未变化断言) |
| `test_ingest_file_partial_change_only_updates_changed_chunks` | 只改动其中一个 chunk 的文本,二次 ingest → 只有该 chunk 的 `content_hash`/`embedding` 更新,其余 `updated_at` 不变 |
| `test_ingest_file_shrink_removes_trailing_chunk_indexes` | 文件变短,二次 ingest → 越界 `chunk_index` 行被删除 |
| `test_ingest_file_concurrent_calls_no_duplicate_rows` | 并发调用同一 `(tenant_id, repository, file_path)` → 唯一约束保护,最终行数正确 |

## Integration Tests（PostgreSQL）

| 场景 | 操作 | 断言要点 |
|---|---|---|
| **租户隔离** | 两个不同 `tenant_id` 各自 ingest 同名文件后,用租户 A 的 `PgVectorContextRetriever` 查询 | 结果只包含租户 A 的 chunk,零租户 B 数据泄露 |
| **仓库隔离** | 同一租户下两个不同 `repository` 各自 ingest | 查询限定 `repository` 后互不混入 |
| **基本检索正确性** | ingest 若干已知 fixture 文本块,用其中一块的原文或高重叠变体作为 query | Top-K 结果包含该 chunk（结构正确性,非排序质量评测,见 Limitations） |
| **`ContextRetriever` 协议一致性** | 用 `PgVectorContextRetriever` 替换 `LocalFixtureContextRetriever` 跑 AF-106 既有的 `ContextAgent` 单元测试用例（不修改 AF-106 测试文件本身,新增一份镜像测试） | `ContextAgent.gather()` 产出结构合法的 `ContextPackage`,证明协议实现正确 |

## 模块导入边界测试

`runtime/context/` 允许导入 pgvector SQLAlchemy 集成库；`packs/delivery/context/`（AF-106 冻结部分）不允许导入 `runtime/context/` 的实现细节，只能通过 `ContextRetriever` 协议引用。

## Negative / Security Tests

- `content` 字段写入前经过 `redact()`（复用 `runtime/tracing.py` 既有函数)——测试构造一段含伪造凭证模式的仓库文本,断言落库内容已脱敏。
- SQL 注入防护：`file_path`/`repository` 含特殊字符（引号、分号）时通过参数化查询正确处理,不拼接 SQL 字符串（用一个含 `'; DROP TABLE` 字样的 `file_path` 值 ingest 并查询,断言表仍然存在且行为符合预期,不是"防注入测试通过是因为侥幸"）。

## 失败判定

- 未变化内容触发重新写入（增量索引失效）。
- 跨租户/跨仓库出现任何数据泄露。
- 迁移 downgrade 意外删除 `vector` 扩展或影响其他表。
- 仓库内容中的疑似凭证模式未被脱敏。

## Limitations

`DeterministicHashEmbedder` 只保证词袋重叠意义上的粗粒度局部性,不代表真实语义理解；"基本检索正确性"测试验证的是"完全或高度重叠的文本能被检索到",不是"语义相关但用词不同的文本能被检索到"——后者需要真实 Embedding 模型,是 M3+ 之后的独立验证工作。
