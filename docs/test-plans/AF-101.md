# Test Plan — AF-101 Create modular monolith application skeleton

> 配套 `docs/design-notes/AF-101.md`；按 `docs/templates/TEST_PLAN_TEMPLATE.md` 结构撰写。状态：Approved（Project Owner，2026-08-02）。Codex 必须先让本清单中的测试跑红，再实现对应代码使其转绿（Test First，`docs/08_TEST_STRATEGY.md`）。

## 测试目标

验证 AF-101 交付的最小骨架满足 Acceptance Criteria（"模块目录存在；只有骨架接口；测试先行"）且不越界：

1. 六个顶层模块包边界存在且可安全 import，不引入禁止的跨层依赖。
2. FastAPI 应用可以被正确构造和启动。
3. `/health` 契约稳定、可被后续 Issue（尤其 AF-102 Docker healthcheck）依赖。
4. 配置缺失/错误时按设计 fail fast，而不是带着错误配置静默运行。
5. 明确划出本 Issue 不测试、留给后续 Issue 的能力边界，避免测试范围蔓延或被误认为已覆盖。

## 测试先行顺序

按 `docs/08_TEST_STRATEGY.md` "Test First" 要求，Codex 应按以下顺序开发，每一步先写测试（预期失败/红），再写最小实现使其通过（绿）：

1. `test_module_boundaries.py`（静态检查，不依赖应用运行，最快建立护栏）
2. `test_settings.py`（`APP_ENV`/`APP_BASE_URL` 加载与校验）
3. `test_app_startup.py`（`create_app()` 在合法/非法配置下的行为）
4. `test_health.py`（`/health` 契约，依赖前三步已经能正常构造出 app）

不允许跳过顺序直接实现全部代码后一次性补测试——如果因故必须调整顺序，需要在 PR 描述中说明原因。

## 单元测试

| 测试 | 覆盖对象 | 断言要点 |
|---|---|---|
| `test_settings.py::test_valid_app_env_accepted` | `settings.get_settings()` | `APP_ENV=development`（以及 `test`、`production`）三个合法值均能成功构造 `Settings`，字段值与环境变量一致 |
| `test_settings.py::test_missing_app_env_raises` | `settings.get_settings()` | 未设置 `APP_ENV` 时抛出明确异常（异常类型/消息在实现中固定下来，测试断言该类型，不断言字符串原文避免脆弱） |
| `test_settings.py::test_invalid_app_env_raises` | `settings.get_settings()` | `APP_ENV=staging`（不在允许值内）时抛出同类异常 |
| `test_settings.py::test_app_base_url_optional` | `settings.get_settings()` | 不设置 `APP_BASE_URL` 时不报错，字段为 `None`／空，设置时原样透传 |
| `test_logging.py::test_configure_logging_is_idempotent` | `logging.configure_logging()` | 重复调用不重复添加 handler、不抛异常 |
| `test_logging.py::test_configure_logging_emits_json` | JSON stdout envelope | 含 timestamp/level/logger/message/trace_id，且为有效 JSON |

### 应用启动测试

| 测试 | 断言要点 |
|---|---|
| `test_app_startup.py::test_create_app_succeeds_with_valid_env` | 合法 `APP_ENV` 下 `create_app()` 返回 `FastAPI` 实例，不抛异常 |
| `test_app_startup.py::test_create_app_fails_fast_without_app_env` | 未设置 `APP_ENV` 时 `create_app()`（或其内部调用的 `get_settings()`）抛出异常，且异常发生在应用对象构造阶段，而不是要等到第一个请求才报错 |
| `test_app_startup.py::test_create_app_fails_fast_with_invalid_app_env` | 非法 `APP_ENV` 值同上 |
| `test_app_startup.py::test_unhandled_exception_returns_structured_error` | 通过一个仅用于测试的临时路由或 monkeypatch 触发未捕获异常，断言全局异常处理器返回结构化 JSON 错误信封（`{"error": {...}}`），且响应体不包含堆栈跟踪文本 |

## 配置缺失和错误配置测试

（与上方"单元测试""应用启动测试"中的对应用例重复列出以满足用户显式要求的分类，实际实现中不必重复写两遍相同测试函数，两个分类共享同一批测试即可）：

- 缺失 `APP_ENV` → fail fast（`test_settings.py::test_missing_app_env_raises`、`test_app_startup.py::test_create_app_fails_fast_without_app_env`）。
- 非法 `APP_ENV` 值 → fail fast（`test_settings.py::test_invalid_app_env_raises`、`test_app_startup.py::test_create_app_fails_fast_with_invalid_app_env`）。
- 明确**不测试**：`DATABASE_URL`/`REDIS_URL`/`TEMPORAL_*` 等其余 `.env.example` 字段的校验——本 Issue 的 `settings.py` 根本不读取它们（见 Design Note "配置加载方案"），因此没有对应行为可测。

## 模块导入边界测试

| 测试 | 断言要点 |
|---|---|
| `test_module_boundaries.py::test_domain_packages_do_not_import_web_framework` | 对 `control_plane`、`runtime`、`gateway`、`models`、`evaluation`、`packs`（含 `packs.delivery`）逐个包做静态源码扫描（建议用 `ast` 解析每个包目录下 `.py` 文件的 `import`/`from ... import` 语句，而不是运行时 `sys.modules` 检查，避免因为测试进程本身已加载 fastapi 而产生假阴性），断言不出现 `fastapi`、`starlette`、`uvicorn` 或任何 Model Provider SDK（如 `openai`、`anthropic`、`litellm`）的 import |
| `test_module_boundaries.py::test_domain_packages_currently_empty` | 断言这六个包目前只含 `__init__.py`（防止有人在骨架阶段提前塞入业务代码，违反 Non-Goals）；此测试预期会在后续 Issue（AF-103 起）开始实现业务逻辑时被有意删除或改造，需在那些 Issue 的 PR 中显式说明为何移除本测试 |
| `test_module_boundaries.py::test_app_layer_can_import_fastapi` | 反向确认：`aegisflow_core.app`/`aegisflow_core.main`/`aegisflow_core.health.router` 允许并且确实 import 了 `fastapi`（防止边界测试写得过严，把合法的应用组装层也一并禁止） |

## 预期结果

- 全部测试通过（绿），不允许出现 `xfail`/`skip` 掩盖真实失败（`docs/08_TEST_STRATEGY.md`"Flaky Test"：Flaky 视为失败，不得靠 retry 掩盖）。
- Coverage 目标：变更行 ≥ 90%（`docs/08_TEST_STRATEGY.md` Coverage 要求）；由于本 Issue 代码量很小，理论上可以做到接近 100%，但不得为了凑数字而删减必要的负向测试。
- PR 中的 Evidence 章节需包含：执行命令、通过/失败数、耗时、以及（如启用）覆盖率数字。

## 失败判定

以下任一情况即判定为本 Issue 未达 Done，不得合并：

- `test_module_boundaries.py` 中任一测试失败（说明存在违反分层依赖方向的 import）。
- `/health` 响应体与本文档定义的契约不完全一致（多字段、少字段、字段值不同）。
- 缺失或非法 `APP_ENV` 时应用仍能"成功"构造（即 fail-fast 行为未生效）。
- 任何测试被标记 `skip`/`xfail` 但未在 PR 描述中给出明确理由和后续跟踪 Issue。
- 测试覆盖了本 Issue 明确排除的能力（例如出现连接真实 PostgreSQL/Redis/Temporal 的测试代码）——这本身说明范围蔓延，即使测试通过也应视为设计违规，需要打回。

## Limitations

- 本测试计划只覆盖骨架层面的正确性，不构成对应用性能、并发安全或未来业务逻辑正确性的任何保证。
- 模块边界的静态检查（`test_module_boundaries.py`）只能检测直接 `import` 语句，无法检测通过字符串反射（`importlib.import_module`）等方式绕过边界的行为；如果后续 Issue 出现此类用法，需要补充更强的静态分析（不在本 Issue 范围内）。
- Health contract 测试目前只验证响应体的精确相等；如果未来该端点需要支持多版本或协商，需要重新设计契约测试，不能简单放宽断言。
