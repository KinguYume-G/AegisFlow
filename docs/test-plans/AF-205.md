# Test Plan — AF-205 Implement Executor Agent contract

> 配套 `docs/design-notes/AF-205.md`。状态：**Draft v2**，等待人工最终 Review。共享契约 §0A 的 v2 测试要求具有优先级。

## Scope

验证 `ExecutionResult`/`TestOutcome` Schema、`ExecutorAgent` 四阶段流程、三类 `ExecutorNodeError` 阶段区分、业务失败（测试不通过）与结构性失败（Executor 崩溃）的区分。使用 `InMemorySandboxRunner`（AF-204），不需要真实 Docker。

## Draft v2 mandatory tests

- 任意 shell 字符串、未知 TestProfile/capability、绝对路径、路径穿越和 symlink escape 均在沙箱调用前拒绝。
- 文件数量、单文件、总内容和 patch 上限分别覆盖边界值与超限值。
- 无结构化测试报告时结果为 `not_available`，不得从 stdout 或 exit code捏造数量。
- 两份全新相同 workspace 产生 byte-identical patch；diff 后两份均由调用方清理。

## 测试先行顺序

1. Schema 边界测试（`changed_files` 去重等）。
2. 正常路径（测试通过）。
3. 业务失败路径（测试不通过/超时）。
4. 三类 `ExecutorNodeError` 分别触发。
5. 幂等/可复现性测试。
6. `runtime/tracing.py` Literal 追加后的回归测试。

## Unit / Component Tests

| 测试 | 断言要点 |
|---|---|
| `test_execution_result_rejects_duplicate_changed_files` | `changed_files` 含重复路径 → 构造被拒绝 |
| `test_executor_agent_happy_path_returns_completed` | `DeterministicPatchReasoner` 产出修改,沙箱测试通过 → `status="completed"`, `test_outcome.status="passed"` |
| `test_executor_agent_test_failure_returns_failed_status_not_exception` | 沙箱命令以非零退出 → 不抛异常,`status="failed"`, `test_outcome.status="failed"` |
| `test_executor_agent_sandbox_timeout_maps_to_failed` | `SandboxResult.status="timeout"` → `ExecutionResult.status="failed"`, `test_outcome.status="timeout"` |
| `test_executor_agent_reasoner_exception_raises_apply_stage_error` | `PatchReasoner.generate_patch` 抛异常 → `ExecutorNodeError(stage="apply")` |
| `test_executor_agent_sandbox_raises_maps_to_sandbox_stage_error` | `SandboxRunner.run` 直接抛异常（非返回失败态) → `ExecutorNodeError(stage="sandbox")` |
| `test_executor_agent_diff_failure_raises_diff_stage_error` | monkeypatch diff 计算函数抛异常 → `ExecutorNodeError(stage="diff")` |
| `test_executor_agent_no_changes_produces_empty_patch` | `PatchReasoner` 返回空映射（无修改）→ `patch=""`, `changed_files=[]`，`status` 仍由测试结果决定 |
| `test_executor_agent_deterministic_across_repeated_calls` | 相同输入调用两次 → `patch`/`changed_files`/`test_outcome` 逐字段相等 |
| `test_executor_agent_does_not_call_github_or_network` | 断言 `ExecutorAgent`/`DeterministicPatchReasoner` 代码路径中不存在任何网络调用（`InMemorySandboxRunner` 本身也不联网） |
| `test_step_trace_record_accepts_executor_agent_literal` | `StepTraceRecord(agent="executor", ...)` 构造成功（回归断言,证明 `runtime/tracing.py` 的 Literal 扩展未破坏既有校验逻辑） |

## 模块导入边界测试

`packs/delivery/executor/` 不允许导入 `gateway/github/*`（不持有 GitHub 凭据，见 Non-Goals）；允许导入 `gateway/sandbox/runner.py`（`SandboxRunner` 协议）。

## Negative / Security Tests

- `workspace_source` 之外的路径不会被读取或写入（`_apply_modifications` 拒绝 `modifications` 映射中出现绝对路径或 `../` 穿越的 key）。
- `DeterministicPatchReasoner` 的固定响应表中若包含超大文件内容（超过合理上限，例如 10MB）→ 拒绝，不静默截断（避免沙箱资源耗尽的误用场景被忽略）。

## 建议执行的命令

```bash
uv run --locked python -m pytest tests/packs/delivery/executor/ -v
uv run --locked python -m pytest tests/runtime/test_tracing.py tests/e2e/test_gate1a.py -v   # 回归 M1
uv run --locked python -m pytest -v
```

## 失败判定

- 业务测试失败（沙箱内测试不通过）被误分类为 `ExecutorNodeError`（结构性异常），或反过来 Executor 自身崩溃被误分类为业务失败——这两者混淆是本 Issue 最核心的失败判定点。
- 相同输入两次调用结果不一致（可复现性被打破）。
- `runtime/tracing.py` 的 Literal 扩展导致任何既有 M1 测试失败。

## 本 Issue 不测试的未来能力

真实 Docker 沙箱集成（AF-204 自身测试覆盖，本 Issue 只用 `InMemorySandboxRunner`）；GitHub 写操作（AF-208）；真实 LLM 驱动的 Patch 生成（M3+）；Policy Gate 集成（AF-210 E2E 覆盖）。
