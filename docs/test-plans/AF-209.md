# Test Plan — AF-209 Implement webhook and tool-call idempotency

> 配套 `docs/design-notes/AF-209.md`。状态：**Draft v2**，等待人工最终 Review。共享契约 §0A 的 v2 测试要求具有优先级。

## Scope

验证 `idempotency_records` 迁移、`IdempotencyLedger` 状态机全部转换路径、并发 `begin()` 唯一性保证、`PostgresIdempotencyGuard` 与 AF-208 协议的集成（含签名调整后的回归）。需要 CI PostgreSQL 服务容器。

## Draft v2 mandatory tests

- `Execute/Reuse/InProgress/FinalFailure` 四种结果穷举，任何状态都不以 `None` 表示。
- 旧 claim token 在 lease 被接管后无法 complete/fail；当前 token 可以完成。
- canonical key 与 arguments hash 改变时形成不同记录；tenant/scope 隔离生效。
- 相同 webhook delivery 并发和跨 service 重建重放均只 dispatch 一次。

## 测试先行顺序

1. 迁移 up/down/reapply。
2. `IdempotencyLedger.begin()` 状态机分支。
3. 并发竞争测试。
4. `complete`/`fail` 转换。
5. `PostgresIdempotencyGuard` 集成 + AF-208 回归。

## Unit / Component Tests

| 测试 | 断言要点 |
|---|---|
| `test_migration_0005_upgrade_creates_table` | 表存在，claim/lease/arguments hash 列与约束正确 |
| `test_migration_0005_downgrade_drops_table` | downgrade 后表消失 |
| `test_migration_0005_reapply_is_idempotent` | up→down→up 不报错 |
| `test_begin_first_call_returns_execute_claim` | 全新 key → `Execute(claim_token)`，数据库行 `status="executing"` |
| `test_begin_succeeded_key_returns_reuse` | 预置 succeeded → `Reuse(result_reference)` |
| `test_begin_live_executing_key_returns_in_progress` | lease 未过期 → `InProgress` |
| `test_begin_expired_retryable_key_returns_new_execute_claim` | lease 过期且可重试 → 新 `Execute` token，attempt 递增 |
| `test_begin_failed_final_key_returns_final_failure` | failed_final → `FinalFailure`，不转换状态 |
| `test_complete_transitions_executing_to_succeeded` | `complete()` 后行状态为 `succeeded`,`result_reference` 正确写入 |
| `test_fail_retryable_transitions_to_failed_retryable` | `fail(retryable=True)` → `failed_retryable` |
| `test_fail_non_retryable_transitions_to_failed_final` | `fail(retryable=False)` → `failed_final` |
| `test_concurrent_begin_only_one_caller_executes` | 并发 10 次 begin → 恰好一个 `Execute`，其余为 `InProgress`/`Reuse` |

## Integration Tests（AF-208 集成回归）

| 场景 | 操作 | 断言要点 |

## 模块导入边界测试

`control_plane/idempotency_ledger.py` 与 `control_plane/domain/idempotency.py` 遵循既有 `control_plane/domain/*` 边界规则；`gateway/github/idempotency_guard.py` 允许同时导入 `control_plane/idempotency_ledger.py` 与 `gateway/github/pull_request.py`（协议实现关系）。

## Negative / Security Tests

- `idempotency_key` 超长或含异常字符时仍能正确写入/查询（不因为字符串内容导致 SQL 注入或截断错位——参数化查询验证）。
- 并发测试覆盖全新 key 与活跃 lease；两种场景都不得返回多个 `Execute`。

## 建议执行的命令

```bash
uv run --locked python -m pytest tests/control_plane/test_idempotency_ledger.py -v
uv run --locked python -m pytest tests/gateway/github/test_idempotency_guard.py tests/gateway/github/test_pull_request.py -v
uv run --locked python -m pytest -v
```

## 失败判定

- 并发 `begin()` 测试出现多于一个 `Execute`——阻塞级正确性失败，直接违反 AC“重复 PR 数 0”。
- 任一状态机转换路径缺失或方向错误。
- AF-208 既有测试在本 Issue 的签名调整后出现回归失败。

## 本 Issue 不测试的未来能力

`EXECUTING` 状态超时自动回收（M3）；Temporal Saga 补偿动作触发（M3）；跨进程/跨重启的 Worker Kill 恢复测试（Gate 2，M3 `18_RELIABILITY_PLAN.md` Chaos 清单）。

## Limitations

本 Issue 的并发测试在单进程内用 `asyncio.gather` 模拟并发,验证的是"同一数据库连接池、同一进程内"的竞争安全性；真正跨进程（多个 Core 实例）的竞争安全性依赖 PostgreSQL 唯一约束本身（数据库级别保证,与进程数量无关），但本 Issue 不专门起多进程做端到端验证——这是数据库唯一约束机制的标准保证,理论上不需要额外证明,若 Human Review 认为需要多进程实测,可在 Evidence 中补充。
