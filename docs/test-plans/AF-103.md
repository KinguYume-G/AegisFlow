# Test Plan — AF-103 Define initial domain model and migrations

> 配套 `docs/design-notes/AF-103.md`；按 `docs/templates/TEST_PLAN_TEMPLATE.md` 结构撰写。状态：Approved v3（2026-08-02），Project Owner 已批准按本计划实施；AI 不得自行合并。

## Scope

验证六张初始领域表（`tenants`/`workflows`/`runs`/`steps`/`approvals`/`audit_events`）能通过 Alembic 迁移正确建立在真实 PostgreSQL 上（本地 AF-102 容器 + CI service container 双重验证），外键（含租户复合外键）/唯一/`CHECK` 约束按设计生效，"Workflow 版本不可覆盖"（含受控的 `status` 流转）与"审计只追加"两条不可变性由数据库触发器强制，迁移可回滚一步并能再次升级，`settings.py` 的 `database_url` 扩展遵循既有 fail-fast 模式。不覆盖任何业务查询逻辑、RBAC/租户过滤中间件、幂等账本。

## 测试先行顺序

1. 本地确认 AF-102 的 `postgres` 服务可用。
2. 先写迁移测试（针对空库跑 `alembic upgrade head` 应该失败，因为迁移文件还不存在）——红灯。
3. 实现 ORM 模型 + 迁移文件（含租户复合外键、两个触发器），使迁移测试转绿。
4. 写触发器与跨租户负向测试（此时应该失败）——红灯 → 触发器/约束就位后转绿。
5. 写 `settings.py` 的 `database_url` 扩展测试（红灯）→ 实现（绿灯）。
6. 本地跑通全部测试后，扩展 `.github/workflows/ci.yml` 加入 `postgres` service container，推送后观察 CI 中同一套验证是否复现通过（CI 环境的 Postgres 镜像版本、网络方式与本地不同，需要独立确认一次，不能假设"本地过了 CI 就一定过"）。
7. 最后跑一次完整 `pytest`（含 AF-101/AF-102 既有套件）确认无回归。

## Integration Tests（需要真实 PostgreSQL：本地 AF-102 容器 + CI service container）

### 迁移生命周期

| 场景 | 操作 | 断言要点 |
|---|---|---|
| 迁移 up | 对空库执行 `alembic upgrade head` | 返回码 0；六张表、全部约束（含租户复合外键）、两个触发器均存在 |
| 迁移幂等 | 重复执行 `alembic upgrade head` | 返回码 0，无报错，无重复对象 |
| 迁移 down | 执行 `alembic downgrade base` | 返回码 0，六张表、约束、触发器均被清除 |
| 降级后再次升级 | 紧接着再执行一次 `alembic upgrade head` | 返回码 0，与首次 up 的结果一致——证明迁移文件本身没有"一次性"的隐藏假设 |

### 正向路径

| 场景 | 操作 | 断言要点 |
|---|---|---|
| 合法插入全链路 | 依次插入 `tenant` → `workflow` → `run`（正确的 `workflow_id`+`workflow_version`）→ `step` → `approval` → `audit_event`，全部使用同一 `tenant_id` | 全部成功 |
| 插入新版本 Workflow | 对同一 `(tenant_id, name)`、不同 `version` 再插入一条 `workflow` | 成功（证明"新增版本"走的是 INSERT，不受触发器影响） |
| `workflows.status` 合法流转 | 对已存在的 `workflow` 行执行 `UPDATE ... SET status = 'superseded' WHERE id = ...`（其余列不变） | 成功——这是修正 Draft v1 逻辑错误后的核心验证点，证明触发器没有"矫枉过正" |

### 负向路径：Workflow 不可变性（核心验收点，替换 Draft v1 的粗粒度版本）

| 场景 | 操作 | 断言要点 |
|---|---|---|
| 修改不可变列 | 对已存在的 `workflow` 行尝试 `UPDATE ... SET definition_hash = '...' WHERE id = ...` | 被触发器拒绝 |
| 修改 `version` | 尝试 `UPDATE workflows SET version = version + 1 WHERE id = ...` | 被触发器拒绝 |
| 非法状态迁移（反向） | 对一条已经是 `superseded` 的行尝试 `UPDATE ... SET status = 'active'` | 被触发器拒绝 |
| 非法状态迁移（跳转到未定义值） | 尝试写入 `CHECK` 约束外的 `status` 值 | 被 `CHECK` 约束拒绝（不依赖触发器） |
| 删除 | 尝试 `DELETE FROM workflows WHERE id = ...` | 被触发器拒绝 |

### 负向路径：审计只追加

| 场景 | 操作 | 断言要点 |
|---|---|---|
| 修改审计行 | 对已存在的 `audit_events` 行尝试任意 `UPDATE` | 被触发器拒绝 |
| 删除审计行 | 尝试 `DELETE` | 被触发器拒绝 |

### 负向路径：跨租户关联（新增，对应审阅意见的核心补充）

| 场景 | 操作 | 断言要点 |
|---|---|---|
| Run 引用他租户 Workflow | 插入一条 `tenant_id = A` 的 `run`，其 `workflow_id`/`workflow_version` 指向一条 `tenant_id = B` 的 `workflow` | 被复合外键约束拒绝（`FOREIGN KEY (tenant_id, workflow_id, workflow_version) REFERENCES workflows (tenant_id, id, version)` 生效） |
| Step 引用他租户 Run | 插入一条 `tenant_id = A` 的 `step`，其 `run_id` 指向一条 `tenant_id = B` 的 `run` | 被复合外键约束拒绝 |
| Approval 引用他租户 Run/Step | 同上模式，分别对 `run_id` 和 `step_id` 测试 | 均被拒绝 |
| Approval 引用同租户其他 Run 的 Step | `approval.run_id` 指向 Run A，`step_id` 指向同租户 Run B 的 Step | 被 `(tenant_id, run_id, step_id)` 三元复合外键拒绝 |
| Run 级 Approval | `run_id` 有效且 `step_id IS NULL` | 插入成功，证明三元复合外键没有误伤 Run 级审批 |
| `workflow_version` 与实际版本不符 | 插入一条 `run`，`workflow_id` 指向一条真实存在、`tenant_id` 正确的 `workflow`，但 `workflow_version` 填一个该 `workflow_id` 实际并不对应的版本号 | 被复合外键约束拒绝（证明 `workflow_version` 不是一个可以随意填写的冗余整数） |

### 其他约束

| 场景 | 操作 | 断言要点 |
|---|---|---|
| 唯一约束违反 | 插入两条 `(tenant_id, name, version)` 完全相同的 `workflows` 行 | 第二条被拒绝 |
| `CHECK` 约束违反 | 插入 `status` 不在允许集合内的 `run`/`step`/`approval` 行 | 被拒绝 |
| 外键指向不存在的 `tenant_id` | 插入引用不存在租户的任意子表记录 | 被拒绝 |

## Fixtures

- 本地：连接到 AF-102 `postgres` 容器的独立测试数据库，禁止指向开发库。测试套件启动前由显式命令迁移到 `head`，结束后由显式 `alembic downgrade base` 清理 schema。
- CI：`.github/workflows/ci.yml` 新增的 `postgres` service container，`DATABASE_URL` 通过 job 级 `env` 注入（见 Design Note "CI 迁移验证"一节的具体 YAML）。
- 两个环境的测试代码应完全一致，只是 `DATABASE_URL` 的值不同——不应该有"只在本地跑"或"只在 CI 跑"的特殊分支逻辑。
- pytest 假定数据库已在 `head`，不在 fixture 内执行 Alembic upgrade/downgrade。每个数据级测试在独立事务中运行并在结束时整体 rollback；预期约束失败使用 nested transaction/savepoint 隔离失败状态。
- **禁止用逐行 `DELETE` 作为 fixture cleanup**：`workflows` 与 `audit_events` 的删除触发器会按设计拒绝该操作。迁移生命周期清理由外层 `downgrade base` 负责。

## 失败判定

以下任一情况判定本 Issue 未达 Done，不得合并：

- 任何负向路径用例（尤其是跨租户关联、Workflow 不可变列修改、审计 UPDATE/DELETE）意外成功。
- `workflows.status` 的合法流转（`active→superseded`）被错误拒绝（说明触发器矫枉过正，重犯 Draft v1 的错误）。
- 迁移 `downgrade base` 后无法再次 `upgrade head`。
- CI 中的 `postgres` service container 未被正确配置，导致迁移相关测试在 CI 中被跳过而非真实执行。
- PR 声称迁移测试"已被 CI 验证"，但实际 `CI / test` 运行记录中看不到 Postgres 连接或迁移步骤的真实输出。
- AF-101/AF-102 既有测试出现任何新增失败。

## 本 Issue 不测试的未来能力

- RBAC、OIDC、租户隔离过滤中间件的请求级行为（AF-401/402/403）——本 Issue 只验证数据库写入路径的约束，不涉及应用层查询过滤。
- 审批/审计相关的业务 API 或路由（AF-305/405）。
- 幂等账本的唯一约束与状态机（AF-209/307）。
- LangGraph PostgresSaver Checkpoint（AF-303）。
- 具体 Agent（Intake/Clarifier/...）对 `steps`/`runs` 的实际读写（AF-104 起）。
- 数据库角色级别的最小权限分离（AF-405/407 附近）。

## Limitations

- 触发器行为是 PostgreSQL 特定机制，无法在 SQLite 等替代方案中等价验证。
- CI 中的 Postgres service container 与本地 AF-102 容器使用相同镜像（`pgvector/pgvector:pg16`）但是两个独立实例，理论上存在"本地通过、CI 环境因细微差异失败"的可能，PR 中如遇到此类差异需要如实记录并排查，不得简单忽略其中一个环境的结果。
- CI 实际使用 `pgvector/pgvector:pg16@sha256:a36250871de0833b8757561c72f2477ef1ddd1101afa4e617fb552e0de514c6b`；该 OCI index digest 于 2026-08-02 核验。升级镜像必须作为可审查变更更新 digest，不能静默跟随 tag 漂移。
- 本测试计划验证"约束存在且生效"，不验证约束带来的错误信息在应用层如何被捕获、转换成用户可读的 API 错误——那属于未来接入统一错误处理的范畴。
