# Test Plan — AF-201 Register GitHub App and verify webhook signature

> 配套 `docs/design-notes/AF-201.md`。状态：**Draft v2**，等待人工最终 Review。共享契约 §0A 的 v2 测试要求具有优先级。

## Scope

验证 `verify_webhook` 四步固定校验顺序、`InstallationTokenProvider` 的缓存/刷新与凭据不泄露、`control_plane/bootstrap.py` 的并发幂等、`AuditEvent` 写入完整性、GitHub App 配置 all-or-none。不连接真实 GitHub（mock HTTP 客户端）；不启动真实 GitHub App。

## Draft v2 mandatory tests

- 有效 delivery 首次 accepted；同一 `(installation_id, delivery_id)` 在 10 分钟内重放返回 409，dispatch 次数仍为 1。
- cache 容量有界、TTL 使用注入的单调时钟；过期后可重新进入，但仍必须重新验签和校验 Schema。
- 不存在基于服务端 `received_at` 推断事件年龄的测试。
- 并发重复 delivery 恰好一个调用获得执行权，其余均拒绝并产生不含 Secret 的审计。

## 测试先行顺序

1. `verify_webhook` 四类拒绝分别测试（签名、时间窗口、结构，各自独立触发,不互相掩盖）。
2. 通过路径测试（全部四步通过）。
3. `AuditEvent` 写入内容测试（通过与拒绝各一条）。
4. `InstallationTokenProvider` 缓存/刷新/失败测试。
5. `control_plane/bootstrap.py` 并发幂等测试（需要 CI 的 PostgreSQL 服务容器）。
6. 配置 all-or-none 测试。
7. 模块边界测试。

## Unit / Component Tests

| 测试 | 断言要点 |
|---|---|
| `test_verify_webhook_rejects_invalid_signature` | 错误签名 → `accepted=False`, `rejection_reason=INVALID_SIGNATURE`,不做后续时间窗口/结构校验（用一个同时签名错误且时间超窗的输入,断言只报告 `INVALID_SIGNATURE`,证明签名校验确实短路在最前） |
| `test_verify_webhook_uses_constant_time_comparison` | 签名比较调用 `hmac.compare_digest`（通过 monkeypatch/spy 断言,而非计时攻击测试） |
| `test_replay_guard_rejects_duplicate_delivery` | 同一 installation/delivery 在 TTL 内第二次 claim → `DUPLICATE_DELIVERY`，dispatch 次数保持 1 |
| `test_verify_webhook_rejects_disallowed_event` | `event` 不在 `allowed_events` 白名单 → `SCHEMA_REJECTED` |
| `test_verify_webhook_rejects_malformed_payload` | Payload 不是合法 JSON 或缺失必需字段 → `SCHEMA_REJECTED` |
| `test_verify_webhook_accepts_valid_delivery` | 全部四步通过 → `accepted=True`, `rejection_reason=None` |
| `test_installation_token_provider_caches_until_near_expiry` | 两次 `get_token()` 调用,`clock` 未推进到缓冲期内 → 只调用一次底层 HTTP 客户端 |
| `test_installation_token_provider_refreshes_after_buffer` | `clock` 推进到过期前 60 秒缓冲期内 → 重新获取 |
| `test_installation_token_provider_error_does_not_leak_private_key` | 底层 HTTP 调用抛异常,断言 `GitHubAppAuthError` 的 `str()` 与其 `__cause__` 链中都不包含私钥 PEM 内容或已获取的 token 字符串 |
| `test_bootstrap_tenant_get_or_create_is_idempotent` | 连续两次调用返回同一行（同一 `id`），第二次不产生新 INSERT |
| `test_bootstrap_tenant_concurrent_create_no_duplicate` | 用 `asyncio.gather` 并发调用多次,数据库最终只有一行,断言唯一约束保护生效 |
| `test_bootstrap_workflow_get_or_create_is_idempotent` | 同上,针对 `(tenant_id, name, version)` 唯一键 |
| `test_settings_github_app_all_four_present_or_absent` | 覆盖全空、全齐、任意 1-3 项缺失场景,后者必须 `ConfigurationError` |

## Integration Tests（FastAPI + PostgreSQL，需 CI Postgres 服务容器）

| 场景 | 操作 | 断言要点 |
|---|---|---|
| **端点拒绝写审计** | 用错误签名 POST `/webhooks/github` | 响应 `401`，body 只含 `{"status":"rejected","reason":"invalid_signature"}`,不含 Payload 回显;数据库出现一行 `decision="deny"` 的 `AuditEvent` |
| **端点接受写审计** | 用正确签名+合法 Payload POST | 响应 `202`；数据库出现一行 `decision="allow"` 的 `AuditEvent`,`tenant_id` 等于 Bootstrap Tenant |
| **配置缺失时端点返回 503** | 清空 GitHub App 环境变量后请求 | `503`,不是 `500`（区分"未配置"与"内部错误"） |

## 模块导入边界测试

`gateway/github/` 允许导入 GitHub REST 客户端库与 `cryptography`/`PyJWT`；`packs/delivery/*` 与 `control_plane/domain/*` 不允许导入这些库。

## Negative / Security Tests

- 私钥 PEM 内容、Installation Token 值均不出现在任何日志输出、异常消息、`AuditEvent.reason` 字段中（专门断言,扫描测试期间捕获的全部日志/异常字符串）。
- TTL 边界由注入的单调时钟验证：TTL 内拒绝，过期后允许新 claim；两种情况都必须先完成签名与 Schema 校验。
- 并发重放同一 `delivery_id`：恰好一次返回 202，其余返回 409；每次拒绝均写审计且不触发 dispatch。

## 失败判定

- 四类拒绝原因中任一未被正确分类,或校验顺序被打乱（例如时间窗口先于签名判断）。
- 私钥/Token 值出现在任何可观测输出中——阻塞级安全失败。
- Bootstrap 并发测试产生重复行。
- 配置缺失时返回非 `503` 状态码。

## 本 Issue 不测试的未来能力

跨重启持久化去重（AF-209）；真实 Installation Token 获取仅在受保护的手动冒烟中验证；多租户/多 Installation 路由（M4）。
