# Test Plan — AF-208 Implement GitHub draft pull request tool

> 配套 `docs/design-notes/AF-208.md`。状态：**Draft v2**，等待人工最终 Review。共享契约 §0A 的 v2 测试要求具有优先级。

## Scope

验证授权前置检查、Scope 固定格式、远端 Marker 幂等检查、`IdempotencyGuard` 注入缝。全程 mock GitHub HTTP 层，不连接真实 GitHub。

## Draft v2 mandatory tests

- 所有风险等级缺少有效 `WriteAuthorization` 都在 GitHub 零调用前失败；伪造、过期、target/base SHA/patch digest 不匹配均失败。
- 覆盖 add/update/delete 的 blob→tree→commit→conditional ref 顺序以及 base SHA 冲突。
- 两个并发相同请求只有一个取得 claim；另一个返回 InProgress/Reuse，Draft PR 总数为 1。
- 模拟每一个 Git Data API 步骤失败，重试只能 reconciliation 同一 Marker 分支，不创建第二个 PR。

## 测试先行顺序

1. 授权前置检查负向测试（最高优先级——安全属性）。
2. 正常创建路径。
3. 远端幂等检查（复用已有 PR）。
4. `IdempotencyGuard` 注入行为测试。
5. Partial Side Effect 场景。

## Unit / Component Tests

| 测试 | 断言要点 |
|---|---|
| `test_create_draft_pr_without_write_authorization_raises` | 任意 risk level 缺少 `WriteAuthorization` → `MissingApprovalError`，且 GitHub 客户端零调用 |
| `test_create_draft_pr_rejects_unbound_or_forged_authorization` | target/base SHA/patch digest 任一不匹配或审批记录非 approved → 拒绝且 GitHub 零调用 |
| `test_create_draft_pr_with_verified_authorization_succeeds` | `ApprovalAuthorizer` 验证全部绑定字段后才取得幂等 claim 并写入 |
| `test_branch_name_matches_fixed_pattern` | 断言分支名精确等于 `aegisflow/run-{run_id}` |
| `test_commit_uses_fixed_bot_author` | 断言 Commit Author 是配置的固定 Bot 身份，不是任何真人 |
| `test_pr_body_contains_valid_marker` | 断言 PR 正文包含精确格式的 `<!-- aegisflow:marker ... -->`,可被同一格式的解析器正确解析回 `run_id`/`idempotency_key` |
| `test_in_progress_claim_never_calls_github` | Guard 返回 `InProgress` → GitHub 读写客户端零调用 |
| `test_remote_marker_check_reuses_existing_pr` | Marker 命中 → reused_existing，Git Data 写 API 与 open PR 均零调用 |
| `test_remote_marker_check_ignores_unrelated_prs` | mock 返回若干 Marker 不匹配的 PR → 视为未命中,继续创建流程 |
| `test_reuse_claim_short_circuits_before_remote_check` | Guard 返回 `Reuse(result)` → 直接返回且 GitHub 零调用 |
| `test_execute_claim_completes_with_same_token` | Guard 返回 `Execute(token)`；成功后使用同一 token complete |
| `test_partial_git_data_failure_is_reconciled` | 每个 Git Data 步骤故障均标记 retryable；重试复用同一 branch/Marker，不创建第二个 PR |

## 模块导入边界测试

`gateway/github/pull_request.py` 复用 `gateway/github/read_tools.py` 的错误类型（导入,不重新定义）；不导入 `control_plane/domain/*`（本 Issue 不直接操作数据库,`IdempotencyGuard` 是纯协议）。

## Negative / Security Tests

- `patch` 内容不经解析执行（写入 Commit 前不对 `patch` 做任何 `eval`/Shell 执行——本工具只是把文本内容提交为文件变更,复用 Git 的标准提交机制）。
- 已成功创建的 PR 再次调用时，原子 Guard 返回 `Reuse`；若本地记录需要恢复，则取得 claim 后通过远端 Marker reconciliation 回填，始终不得产生重复 PR。
- 授权前置检查不能被任何参数组合绕过（穷举测试三种 `risk_level` × `approval_reference` 是否为 `None` 的组合，只有 `L3`+`None` 一种应该失败）。

## 失败判定

- `MissingApprovalError` 场景下仍然调用了任何 GitHub 写 API——阻塞级安全失败。
- 远端 Marker 检查未能阻止重复创建——阻塞级可靠性失败。
- 分支名/Marker 格式与设计文档不一致（破坏未来 AF-209/AF-210 对这些格式的假设）。

## 本 Issue 不测试的未来能力

PostgreSQL Idempotency Ledger 的表与 lease 实现（AF-209）；真实 GitHub API E2E（AF-210）；Merge/原生 Review 操作（Non-Goals）。AF-208 自身仍必须使用满足协议的 InMemory 原子 Guard 完成并发测试。

## Limitations

真实 GitHub 的最终一致性仍可能使远端搜索短暂不可见，因此正确性以本地原子 claim 为第一道保证、Marker reconciliation 为恢复保证。任何能产生重复 PR 的竞态均为阻塞失败，不作为已知限制接受。
