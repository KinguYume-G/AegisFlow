# Test Plan — CI-001 Add foundational CI

> 配套 `docs/design-notes/CI-001.md`；按 `docs/templates/TEST_PLAN_TEMPLATE.md` 结构撰写。状态：Approved（2026-08-02）。

## Scope

验证新增的 GitHub Actions workflow 能够：(1) 在 PR 上自动触发；(2) 真实复现 AF-101/AF-102 已建立的 pytest 套件与覆盖率门槛；(3) 在测试失败时可靠标红、在测试通过时可靠转绿——即"证明这道 Gate 真的会拦人"，而不仅仅是"YAML 语法正确"。不覆盖 Branch Protection 配置生效后的长期行为（那是运营层面的持续状态，不是本 Issue 一次性可测的东西）。

## 测试先行顺序

由于本 Issue 的交付物是 CI 本身，"测试先行"在这里的含义是：**先让 CI 在一个已知会失败的状态下运行一次，确认它确实会标红，再让它在正确状态下运行，确认转绿**——这是对"测试基础设施"这件事本身的验证顺序，不是传统意义上"先写 pytest 用例再写实现"（本 Issue 不新增任何 Python 业务代码或测试用例）。

1. 从最新 `origin/main` 新建分支 `infra/CI-001-foundational-ci`（不复用 AF-102 遗留分支）。
2. 本地（或 CI 环境）确认 `uv sync --locked` 在当前锁文件下能成功。
3. 本地确认 `uv run --locked python -m pytest --cov=aegisflow_core --cov-report=term-missing` 能成功（复用 AF-101/AF-102 已有套件，不应有意外失败）；本地确认 `docker compose build core` 能成功。
4. 提交 workflow 文件到 PR 分支，观察 GitHub Actions 首次真实运行。
5. 在同一 PR 里新增临时探测文件 `tests/test_ci_gate_probe.py`（内容为一个明确必然失败的断言，例如 `def test_ci_gate_probe(): assert False, "intentional CI gate probe"`），推送并观察 Actions 标红。**不得**通过改坏 `uv.lock` 或修改既有测试文件来制造失败——前者会和"验证依赖锁定"这个目的自相矛盾，后者会污染既有测试文件的提交历史。
6. 删除 `tests/test_ci_gate_probe.py`，推送并观察 Actions 转绿。
7. 确认 PR 页面的 Checks 区块清晰展示上述两次状态（context 名称为 `CI / test`），任何人不需要额外工具就能看懂。

## Integration Tests（workflow 自身的端到端验证）

| 场景 | 操作 | 断言要点 |
|---|---|---|
| 正常触发 | 对目标分支开 PR | Actions 页面出现名为 `CI` 的 workflow run，job 名为 `test`（Required Check context 即 `CI / test`），与 `docs/design-notes/CI-001.md` 中定义的一致 |
| Runner 环境符合预期 | 检查 Actions 日志顶部的 Runner 信息 | 确认使用 `ubuntu-24.04`（不是漂移到其他版本），且单次运行未超过 `timeout-minutes: 15` |
| 依赖锁定生效 | 检查 Actions 日志中 `uv sync --locked` 步骤 | 步骤成功，日志显示按 `uv.lock` 精确安装，无版本重新解析提示；`setup-uv` 步骤日志确认安装的是 pin 的 `0.11.31` |
| 套件真实执行 | 检查 Actions 日志中 `pytest` 步骤 | 输出显示 AF-101/AF-102 已有全部测试文件均被收集并执行（不是 0 collected 或被意外过滤） |
| Docker 相关测试未被跳过 | 检查 `test_docker_compose_config.py` 在 CI 日志中的具体输出 | 确认该测试在 `ubuntu-24.04` runner 上是真实执行（PASSED），而不是显示 `SKIPPED`（若显示 SKIPPED，说明 CI runner 环境与预期不符，需要在 PR 中说明原因，不得忽略） |
| Core 镜像构建 | 检查 Actions 日志中 `docker compose build core` 步骤 | 使用非 Secret 测试占位变量渲染 Compose；返回码 0，构建日志中 `uv sync --locked` 成功；没有触发 `up` 或端口绑定 |
| 覆盖率门槛生效 | 检查 `--cov-report=term-missing` 输出 | 显示总覆盖率数字，且该数字来自 `pyproject.toml` 已配置的 `fail_under=90` 门槛判定路径 |
| **刻意失败 → 标红** | 新增 `tests/test_ci_gate_probe.py`（含明确必然失败的断言）并推送 | 对应 Actions run 状态为失败（红叉），PR 页面 Checks 区块（`CI / test`）清晰显示不通过，失败原因在日志中可直接定位到 `test_ci_gate_probe` |
| **修复 → 转绿** | 删除 `tests/test_ci_gate_probe.py` 并推送 | 新的 Actions run 状态为成功（绿勾） |
| 覆盖率门槛真的会拦人（可选加强项，若时间允许） | 临时删掉一个已有测试文件的大部分内容（降低覆盖率到 90% 以下）并推送，之后撤销 | Actions 因覆盖率不足而失败，即使所有剩余用例本身都通过；证明 `fail_under=90` 不是摆设 |

## 配置缺失和错误配置测试

| 场景 | 断言要点 |
|---|---|
| workflow 文件本身 YAML 语法错误（作为一次性验证，不留在最终版本里） | GitHub 会在 PR 的 "Actions" / workflow 文件本身报告解析错误，Codex 应在实现阶段本地过一遍语法（`actionlint` 若可用）避免把这类错误留到评审阶段才发现 |
| Action 版本 pin 缺失或使用了可变 tag（如 `@v4`） | 属于 Code Review 检查项而非运行时可自动检测的失败，Reviewer 需要在人工 Review 阶段核对（本 Test Plan 在此明确要求，供 Reviewer 参照） |

## Negative / Security Tests

- 确认 workflow 的 `permissions:` 显式声明为 `contents: read`（而不是使用 GitHub 默认的更宽泛权限）——检查 workflow 文件内容而非运行时行为。
- 确认 workflow 中不出现任何 `secrets.*` 引用（本 Issue 不需要任何 Secret；若未来需要，应该是新 Issue 的范畴且需要更新 Security Impact）。
- 确认两个引用的 Action 均以完整 40 位 commit SHA 引用，而不是 `@main`/`@v4` 等可变引用——这是防止"上游 Action 被劫持后自动拉取恶意版本"的供应链保护，必须在 PR Review 阶段逐字核对，具体值应为 `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1` 与 `astral-sh/setup-uv@c771a70e6277c0a99b617c7a806ffedaca235ff9`，不能只看 Action 名字或近似值。
- 确认 `actions/checkout` 步骤显式声明 `persist-credentials: false`。
- 确认 Branch Protection 配置（若本次 PR 范围内已执行）与 Design Note"Branch Protection 配置"一节的 6 步流程和具体规则完全一致：`required_approving_review_count: 0`（账号条件过渡值，不是遗漏）、Required Status Check 为 `CI / test`、禁止 force push、禁止删除分支、`enforce_admins: true`。若配置由 Codex 之外的角色（我）执行，应在 PR 或后续记录中注明执行者与执行时间，不得含糊。

## 建议执行的命令

```bash
# 本地预检（在推送前确认基本可行）
uv sync --locked
uv run --locked python -m pytest --cov=aegisflow_core --cov-report=term-missing
docker compose build core

# 之后通过 git push 触发真实的 GitHub Actions 运行，
# 证据以 Actions 运行链接（形如
# https://github.com/KinguYume-G/AegisFlow/actions/runs/<run_id>）
# 及其日志摘录为准，而不是本地命令输出。
```

## 预期结果

- 正常状态下，Actions run 全绿，日志显示套件全部通过、覆盖率达标。
- 刻意失败状态下，Actions run 标红，且失败原因在日志中清晰可定位（不是超时或环境错误这类噪音失败）。
- 两种状态的 Actions 运行链接均记录在实现 PR 的描述或评论中，作为"CI 确实会拦截问题"的证据，而不只是"CI 文件语法正确"。

## 失败判定

以下任一情况判定本 Issue 未达 Done，不得合并：

- 只提供了"绿灯"证据，没有实际验证过"红灯"场景——这样无法证明 CI 真的能拦截坏改动，等同于没有测试这道 Gate 本身。
- `test_docker_compose_config.py` 在 CI 中被跳过（`SKIPPED`）而 PR 未对此给出合理解释。
- 覆盖率门槛（90%）在 CI 日志中没有实际的判定痕迹（例如命令没有正确带 `--cov` 参数，导致门槛从未真正生效）。
- 任一 Action 引用使用可变 tag 而非完整 commit SHA，或 SHA 与 Design Note 中核验过的值不一致。
- workflow 声明了超出 `contents: read` 的权限，或引用了任何 `secrets.*` 却没有对应的、经批准的用途。
- 未在最终绿灯后展示精确 payload 并获得 Project Owner 再次授权，就调用 `gh api` 修改 Branch Protection。
- 红灯验证是通过破坏 `uv.lock` 或修改既有测试文件实现，而不是使用专用的 `tests/test_ci_gate_probe.py`。
- 分支基于 AF-102 的旧分支（`feat/AF-102-compose-foundation`）而非从最新 `origin/main` 新建。
- AF-103 在 CI-001 完成、Branch Protection 生效前被翻牌为 `status:ready` 或已开始实现。

## 本 Issue 不测试的未来能力

- Docker 镜像的完整 `up` + 端到端 healthcheck 集成（本 Issue 只做 `docker compose build core`，不 `up`）。
- AF-507（M5 Prompt Regression Gate）的评测数据集回归门禁——与本 Issue 是完全不同的 CI 门禁，届时会有独立 Design Note。
- lint/typecheck（ruff/mypy）相关的任何 CI 步骤（沿用 AF-101/AF-102 的排除范围）。
- 依赖/Secret 泄露的自动化安全扫描（`uv` 生态漏洞审计、Secret Scanning、Dependabot alerts）——已在 Design Note 中明确列为独立的后续安全加固 Issue，不占用本次"foundational"CI 的范围。
- 部署流水线、Release Tag 自动化。
- Branch Protection 配置生效后的长期运营验证（例如"半年后是否仍然生效"，或"第二位 Reviewer 加入后 `required_approving_review_count` 是否已改回 1"）——那是持续治理观察，不是本 Issue 一次性测试范畴。

## Limitations

- 本测试计划依赖真实推送到 GitHub 触发 Actions；无法在纯本地环境完整验证"标红/转绿"这两个关键场景，必须通过实际 PR 完成。
- 覆盖率门槛的"加强验证"（临时降低覆盖率证明门槛生效）是可选项，如果因为时间/篇幅被跳过，PR 必须明确说明这一遗漏，不能默认已验证。
- 本 Test Plan 不执行破坏性的 main 直推探测；Branch Protection 配置后通过只读 API 回读规则，并由 CI-001 PR 的受保护 Human Merge 证明 Gate 可用。
- `required_approving_review_count: 0` 是账号条件下的已知过渡状态，不是本 Test Plan 需要"修复"的缺陷；但需要在证据记录中明确写出这一状态，避免日后被误读为"本来就该是 0"。
