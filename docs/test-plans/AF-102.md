# Test Plan — AF-102 Create Docker Compose foundation

> 配套 `docs/design-notes/AF-102.md`；按 `docs/templates/TEST_PLAN_TEMPLATE.md` 结构撰写。状态：Approved（2026-08-02）。

## Scope

验证一条命令能否把 Core、PostgreSQL、Redis 三个服务用 Docker Compose 拉起，三者 healthcheck 均通过，配置全部来自占位符（`.env.example`），且不破坏 AF-101 已交付并通过的应用层测试套件。本 Issue 是基础设施/配置交付，证据以 `docker compose` 等 CLI 命令的真实输出为主，辅以少量可跳过的 pytest 冒烟测试。

## 测试先行顺序（沿用 AF-101 的 Test First 精神，适配基础设施类 Issue）

1. `docker compose config`（静态校验 YAML 语法与变量插值）——最快、不需要真正拉起容器，先确保文件本身写对。
2. `docker build`（单独构建 Core 镜像）——在起完整 stack 之前先确认镜像能构建成功。
3. `docker compose up -d` + 逐服务 healthcheck 观察——验证编排层面的启动顺序和健康判定。
4. 复用 AF-101 既有 `pytest` 套件（不改动，只是回归确认未被破坏）。
5. 负向场景（缺失 `.env`、错误端口占用等）。

## Unit Tests

本 Issue 不新增应用层单元测试（不修改 `src/aegisflow_core/`）。唯一新增的是一个基础设施配置层面的冒烟测试：

| 测试 | 覆盖对象 | 断言要点 |
|---|---|---|
| `tests/test_docker_compose_config.py`（已批准新增）| `compose.yaml`、`Dockerfile`、`.dockerignore`、`.env.example` | 校验渲染、服务/环境 allowlist、回环端口、healthcheck、依赖条件、digest pin、builder-only uv、缺失变量 fail-fast 与构建上下文排除规则 |

## Component Tests

**基本不适用**——`postgres`/`redis`/`core` 三个服务本身是官方镜像或复用 AF-101 已验证的 Core 应用，本 Issue 不产出需要 Component 级隔离测试的新组件代码；相关验证下沉到"建议执行的命令"一节的 CLI 检查。

## Integration Tests（对应用户要求里的"应用启动测试""API health contract 测试"在容器语境下的等价物）

以下均为**命令 + 断言输出**形式，不是 pytest 用例（除非人工要求把它们也包装成 `subprocess`-based pytest，那样会显著拉长本 Issue 的执行时间，默认不采纳，见 Limitations）：

| 场景 | 命令 | 断言要点 |
|---|---|---|
| Compose 文件语法与插值 | `docker compose config` | 输出可解析的完整配置，无报错；三个服务名（`core`/`postgres`/`redis`）均出现在输出中 |
| Core 镜像构建 | `docker compose build --pull core` | 返回码 0，构建日志中 `uv sync --locked` 步骤成功（无依赖漂移错误） |
| 整体启动 | `docker compose up -d` | 返回码 0 |
| 服务健康状态 | `docker compose ps` | 三个服务的 `STATUS` 列均显示 `healthy`（等待 `start_period` + `retries` 覆盖的时间窗口后再检查，不在容器刚起来的一瞬间断言） |
| Core health contract（容器语境） | 宿主机执行 `curl -s http://127.0.0.1:8000/health`（或人工确认的等效端口） | 返回体精确等于 AF-101 契约 `{"status": "ok", "service": "aegisflow-core"}`，与本地非容器直跑时行为一致——证明 Docker 化没有改变应用行为 |
| Postgres 可连通性（不代表 Core 已集成） | `docker compose exec postgres pg_isready -U <POSTGRES_USER>` | 返回 `accepting connections` |
| Redis 可连通性 | `docker compose exec redis redis-cli ping` | 返回 `PONG` |
| 清理 | `docker compose down -v` | 返回码 0，`docker volume ls` 中不再出现 `postgres_data` 对应的卷 |

## 应用启动测试（AF-101 回归，容器化后不应变化）

| 测试 | 断言要点 |
|---|---|
| 复用 `pytest -v`（AF-101 既有套件，不修改） | 在**非容器**环境下（本机 `uv run pytest -v`）依旧全部通过，证明本 Issue 没有意外改动 `src/aegisflow_core/` 导致回归 |
| （可选，若决策认可）容器内运行 `docker compose exec core uv run pytest -v` | 证明打包进镜像的代码路径与本机一致；本设计默认**不**强制要求，因为会显著拉长 CI/本地验证时间，且本 Issue 的核心目标是"能启动+healthcheck 通过"而不是"容器内跑单测"——是否纳入见 Limitations |

## 配置缺失和错误配置测试

| 场景 | 操作 | 预期结果 |
|---|---|---|
| `.env` 不存在（只有 `.env.example`） | 清除必需变量后执行 `docker compose config --quiet` | `${VAR:?message}` 在创建任何容器前返回非 0，并指出第一个缺失变量 |
| `POSTGRES_PASSWORD` 为空字符串 | 环境中显式设为空后执行 `docker compose config --quiet` | 返回非 0，并显示 `POSTGRES_PASSWORD is required` |
| 端口被占用（如本机已有其他进程占 5432） | 提前在宿主机监听 5432 后再 `docker compose up` | `docker compose up` 报端口绑定失败并退出非 0，错误信息明确指向端口冲突 |

## 模块导入边界测试

**不适用于本 Issue**——AF-101 已建立的 `tests/test_module_boundaries.py` 属于应用层测试，本 Issue 不修改 `src/aegisflow_core/`，因此该测试的通过与否只是"未被破坏"的回归确认，不属于本 Issue 新增的测试范畴。若 Codex 在实现过程中发现 `Dockerfile`/`compose.yaml` 迫使应用代码发生任何变化，应立即停止并请求人工输入（这本身就意味着范围已经越出 Non-Goals）。

## Negative / Security Tests

- 确认 `compose.yaml` 中 Core/Postgres/Redis 端口都解析为 `127.0.0.1`，而不是裸端口或 `0.0.0.0`。
- 确认 `.dockerignore` 生效：构建后检查镜像内不包含 `.git/`、`.env`（若本机存在）、`tests/`、`docs/` 等目录（`docker run --rm aegisflow-core:test ls -la /app` 或等效检查）。
- 确认 `docker build` 产物中没有把任何 `.env` 真实值 bake 进镜像 layer（本 Issue 的 Dockerfile 设计不 `COPY .env`，此项测试是防止未来有人误改 `.dockerignore` 或 `Dockerfile` 的回归护栏）。

## Fault Injection

**不适用（N/A）**。Kill worker、依赖服务中断等故障注入属于 Gate 2（AF-309），本 Issue 的服务尚未被任何业务逻辑使用，没有可观察的"故障恢复"行为可供注入测试。

## Fixtures

- 容器内 pytest 不采纳；runtime 镜像有意排除测试源码与开发依赖。

## 建议执行的命令

```bash
docker compose config
docker build -t aegisflow-core:test .
docker compose up -d
docker compose ps
curl -s http://127.0.0.1:8000/health
docker compose exec postgres pg_isready -U <POSTGRES_USER>
docker compose exec redis redis-cli ping
docker compose logs core --tail 50
docker compose down -v
uv run pytest -v   # 本机直跑，确认 AF-101 回归套件未受影响
```

具体命令随决策 1/2/5/7 的最终选择微调（例如端口号、`POSTGRES_USER` 占位符替换成的真实开发值）；PR 中必须记录**实际执行**的命令与输出，不得照抄本模板而未真实运行。

## 预期结果

- `docker compose config`、`docker build`、`docker compose up` 均返回码 0。
- 三个服务健康状态最终全部为 `healthy`（允许 `start_period` 内的短暂 `starting` 状态）。
- `/health` 响应体与 AF-101 契约逐字节一致。
- 负向场景（缺 `.env`、空密码、端口冲突）均按预期失败，且失败信息可定位到具体原因，不是模糊的通用错误。
- AF-101 既有 `pytest` 套件在本机（非容器）环境下 100% 保持通过。

## 失败判定

以下任一情况判定本 Issue 未达 Done，不得合并：

- `docker compose up` 之后任一服务长期停留在 `unhealthy` 或 `exited`。
- `/health` 响应体与 AF-101 既定契约不一致（说明 Non-Goals 被违反，应用代码被意外改动）。
- `.env` 缺失时容器仍"成功"启动并接受空/默认密码（说明"配置来自占位符"的安全前提被破坏）。
- Postgres/Redis 端口绑定到 `0.0.0.0`（对外暴露），除非该项已被决策 5 的最终确认结果明确改变。
- AF-101 既有 pytest 套件出现任何新增失败。
- Docker 相关命令的执行证据在 PR 中缺失或明显是编造的（例如貌似复制粘贴自本文档模板而非真实终端输出）。
- 执行环境缺少 Docker 但 PR 却声称"已验证通过"而未如实注明限制。

- Temporal 相关的一切（AF-301 起）。

- 性能/并发（AF-511）。
- 任何真实 Secret 参与的测试。

## Evidence

- 执行环境：Windows 11 + Docker Engine 29.4.3 + Docker Compose 5.1.3，Docker Desktop daemon 可用。
- Test First 红测：`uv run --locked python -m pytest -q` → `4 failed, 21 passed, 5 errors`，均由 AF-102 文件尚未创建导致。
- 静态与回归：`.venv\\Scripts\\python.exe -m pytest -q` → `30 passed`；`docker compose config --quiet` → 0。
- 构建：`docker compose build --pull core` → 0；锁定依赖成功，runtime 不包含 `/bin/uv`。
- 集成：`docker compose up -d --wait --wait-timeout 120` → 0；Core、PostgreSQL、Redis 最终均为 `healthy`。
- 契约与依赖：`/health` → `{"status":"ok","service":"aegisflow-core"}`；`pg_isready` → `accepting connections`；`redis-cli ping` → `PONG`。
- 安全：Core 用户为 `appuser`；三端口只绑定 `127.0.0.1`；镜像内无仓库 `.git`、`.env`、`tests`、`docs`；缺失 `POSTGRES_PASSWORD` 时 `docker compose config --quiet` 返回 1 并指出必需变量。
- 幂等与清理：重复 `docker compose up -d --wait` 成功且未创建重复容器；`docker compose down --volumes` 删除本次测试容器、网络和空测试卷。
- 已知限制：未注入真实 Secret；未执行刻意占用宿主端口的破坏性冲突测试，端口与必需变量失败路径由静态测试覆盖。

## Limitations

- 本测试计划的大部分证据依赖真实 Docker 环境；如果 Codex 的执行环境没有可用的 Docker daemon（沙箱/CI 限制），则"Integration Tests"一节的多数命令无法真正执行，只能退化到 `docker compose config` 语法校验。这种情况下 PR 必须显式声明限制，并建议由人工在有 Docker 的机器上补跑一次验证后再合并，不得把未执行的命令描述成已验证通过。
- `docker compose config` 冒烟与静态安全护栏已纳入 pytest；容器内 pytest 未纳入，因为 runtime 有意不包含测试源码和开发依赖。
- Postgres/Redis 健康检查只验证"进程已就绪"，不验证具体数据库/键空间内容是否符合未来 AF-103 的领域模型期望——那是 AF-103 自己的测试范畴。
