# Design Note — AF-207 Implement deterministic Policy Gate v0

> 状态：**Draft v2**，等待人工最终 Review。依赖 AF-107（已合并）。按 M2-SHARED-CONTRACTS §15 顺序排在 AF-204 之后（无直接代码依赖，仅为顺序纪律）。Codex 在获得批准前不得实现。v2 行为以共享契约 §0A 为准。
> 前提文档：`docs/design-notes/M2-SHARED-CONTRACTS.md`（第 9、13、16 节）。GitHub #26。ADR-0007、`09_SECURITY_BASELINE.md`。

## Draft v2 implementation contract

- Policy 输入增加可信 `ExecutionScope(repository_target, allowed_capabilities)`；它只能由验签 webhook、Installation 配置和运行时组装层构造。
- 禁止从 `NormalizedRequest.source_ref`、PRD、Issue body 或 Plan 自报字段推导授权仓库。
- 第一条规则比较规范化后的 `RepositoryTarget(owner, repo, base_ref, installation_id)`，其后再检查 capability 与风险上限。
- 规则引擎保持确定性、默认拒绝且不调用 LLM。

## Problem

Executor 消耗真实资源（Docker 容器、真实仓库读取）之前，需要一个确定性、可审计、LLM 不可覆盖的前置门禁，拒绝越权仓库、越权工具能力、超出风险上限的 Plan。

## Objective

按 Issue #26 AC（"LLM 不可覆盖规则；拒绝有审计；规则有单测"），实现 `PolicyGate.evaluate(plan, request) -> PolicyDecision`，三条固定顺序规则，每次调用写一行 `AuditEvent`。

## Non-Goals

- 不做 RBAC/身份校验（role/tenant 的完整 Contextual Policy 是 AF-401–AF-409，M4 范围；v0 只做仓库/工具能力/风险三项确定性规则）。
- 不产生 `StepTraceRecord`/Langfuse Trace（本 Issue 不是 LLM 调用，见 SHARED-CONTRACTS §9.3）。
- 不接入图（AF-210 范围）。
- 不做预算/成本维度的规则（`Measurement(status="not_available")` 在 M2 阶段恒定，没有真实数值可比较）。

## Affected Modules

- 新增 `gateway/policy/__init__.py`、`gate.py`（`PolicyGate`/`PolicyDecision`/`PolicyConfig`）、`config.py`（配置加载）。
- 新增 `packs/delivery/contracts/policy_decision.py`——**注意**：`PolicyDecision` 放在 `contracts/` 是因为它是跨模块共享的数据契约（图状态、AuditEvent 写入都需要引用它），但 `PolicyGate` 本身（规则引擎逻辑）放在 `gateway/policy/`，与其他 Agent 的"契约在 `contracts/`、实现在 `packs/delivery/<agent>/`"模式保持同构，只是 Policy Gate 不属于六个命名 DeliveryPack Agent 之一（`02_ARCHITECTURE.md` 六 Agent 契约表未列出 Policy Gate，它是 Planner 与 Executor 之间的独立网关，位置放在 `gateway/` 而非 `packs/delivery/` 是刻意的架构对齐）。
- 新增 `tests/gateway/policy/`。
- 修改 `docs/21_TRACEABILITY_MATRIX.md`。

## Proposed Flow

### `PolicyDecision`（`packs/delivery/contracts/policy_decision.py`）

```text
class PolicyDecision(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)
    schema_version: Literal[1] = 1
    decision: Literal["allow", "deny"]
    violated_rule: Literal["repository_scope", "tool_capability_scope", "risk_ceiling"] | None
    reasons: list[str]

    @model_validator(mode="after")
    def state_must_be_consistent(self) -> "PolicyDecision":
        if self.decision == "allow" and (self.violated_rule is not None or self.reasons):
            raise ValueError("allow decision cannot carry a violated rule or reasons")
        if self.decision == "deny" and (self.violated_rule is None or not self.reasons):
            raise ValueError("deny decision requires a violated rule and at least one reason")
        return self
```

### `PolicyConfig`（`gateway/policy/config.py`）

```text
class PolicyConfig(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)
    schema_version: Literal[1] = 1
    allowed_repository: str
    enabled_tool_capabilities: frozenset[ToolCapability]
    max_allowed_risk_level: Literal["L1", "L2", "L3"]

def load_policy_config_from_settings(settings: Settings) -> PolicyConfig: ...
```

### `PolicyGate`（`gateway/policy/gate.py`）

```text
_RISK_ORDER = {"L1": 1, "L2": 2, "L3": 3}

class PolicyGate:
    def __init__(self, config: PolicyConfig): ...

    def evaluate(self, plan: Plan, scope: ExecutionScope) -> PolicyDecision:
        repository = scope.repository_target
        if repository != self._config.allowed_repository_target:
            return _deny("repository_scope", [f"repository {repository!r} is not allowed"])

        requested = {tool.tool_name for task in plan.tasks for tool in task.required_tools}
        disallowed = requested - self._config.enabled_tool_capabilities
        if disallowed:
            return _deny("tool_capability_scope", [f"capability {name!r} is not enabled" for name in sorted(disallowed)])

        if _RISK_ORDER[plan.risk_level] > _RISK_ORDER[self._config.max_allowed_risk_level]:
            return _deny("risk_ceiling", [f"risk level {plan.risk_level} exceeds configured maximum"])

        return PolicyDecision(decision="allow", violated_rule=None, reasons=[])
```

三条规则**固定顺序、短路求值**——第一条违反的规则即为最终 `violated_rule`，不做规则累积（镜像 AF-105 Clarifier 五规则的固定顺序写法）。

## State Ownership / External Side Effects / Idempotency

- **State Ownership**：`PolicyGate` 本身无状态（`PolicyConfig` 是启动时加载的不可变配置）；调用方（AF-210 图节点）负责把每次 `evaluate()` 结果写入 `audit_events`。
- **External Side Effects**：无。
- **Idempotency**：`evaluate()` 是纯函数，相同输入恒定产出相同 `PolicyDecision`，天然幂等，不需要 Ledger。

## Failure Modes

| 场景 | 预期行为 |
|---|---|
| 仓库不匹配 | `deny`，`violated_rule="repository_scope"` |
| 请求未启用的工具能力 | `deny`，`violated_rule="tool_capability_scope"`，`reasons` 列出全部违规能力（不是只报第一个） |
| 风险超过上限 | `deny`，`violated_rule="risk_ceiling"` |
| 多条规则同时违反 | 只报告**第一条**（顺序：repository → tool_capability → risk），其余规则不再评估（与 Clarifier 五规则模式一致，避免"报告了但没完整检查"的歧义——固定顺序意味着调用方每次只能从第一个失败点开始修复，重新提交后才能看到后续规则） |
| `PolicyConfig` 加载失败（配置缺失） | `ConfigurationError`，与 AF-109/AF-201 一致的 fail-fast 风格 |

## Security Impact

Risk Level L1（确定性规则评估，无外部副作用）。ADR-0007 的核心规则"LLM 不可覆盖 Policy 结论"通过**架构隔离**保证：`PolicyGate.evaluate()` 不接受、不调用任何 LLM/Reasoner 端口，纯规则引擎,不存在"被 Prompt 影响"的攻击面。`19_THREAT_MODEL.md` 的 `Tool Abuse` 威胁通过 `tool_capability_scope` 规则缓解。
