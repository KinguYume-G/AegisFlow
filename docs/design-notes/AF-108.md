# Design Note — AF-108 Implement clarification HITL interface

> 状态：**Approved v4**。M1 Shared Contracts v4 已通过 PR #84 Human Review/Merge；AF-105–AF-107 已 Human Merge/verified；AF-108 实现已获 Project Owner 授权并启动。

## Problem and Objective

Clarifier 信息不足时需要一个可暂停、可关联 run、可拒绝错误或重复回复的接口。AF-108 提供 LangGraph replay-safe 的进程内实现，为 AF-110 演示使用；生产 durable HITL 仍属于 AF-304。

## Non-Goals

不建表、不接 Temporal、不跨进程恢复、不发送通知、不实现 Web endpoint。

## Affected Files

- `src/aegisflow_core/packs/delivery/clarifier/hitl.py`
- `tests/packs/delivery/clarifier/test_hitl.py`
- `docs/21_TRACEABILITY_MATRIX.md`

不得创建顶层 `packs/delivery/hitl.py`，也不得修改 AF-105 已交付的 agent/ports/fakes。

## Design

```text
class ClarificationStatus(StrEnum): PENDING, ANSWERED

request_clarification(run_id, step_key, questions) -> request_id
submit_response(request_id, run_id, answers) -> ClarificationOutcome
get_status(request_id) -> ClarificationStatus
```

`InMemoryClarificationGateway` 必须显式注入 `IdGenerator`。内部维护 `(run_id, step_key) → request_id` 和 request_id → record 两个索引。

- 同一 `(run_id, step_key)` 重复 request 返回同一个 ID，不新增、不覆盖 questions/answers/status。
- submit 依次校验 request 存在、run_id 相同、状态 PENDING；成功后原子地转为 ANSWERED。
- 未知请求、run 不匹配、重复提交分别抛独立异常。
- Gateway 只存储答案；是否充分由 AF-105 `ClarifierAgent.resolve()` 负责。

## State, Failure and Security

- 状态只在进程内，重启丢失，不是业务事实源。
- request 是可重试幂等操作；submit 按 Issue AC 明确拒绝第二次提交。
- run_id 校验防止拿到别的 request_id 后跨 run 注入答案。
- answers 只作为数据保存，不解释执行。
