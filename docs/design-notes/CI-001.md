# Design Note — CI-001 Add foundational CI (pytest regression + branch protection readiness)

> 状态：Approved（2026-08-02）。Project Owner 已批准全部修正与四项 Resolved Decisions。
> 实施边界：只建立基础 CI 与 Branch Protection readiness；不开始 AF-103，不引入部署或业务代码。
> **本 Issue 不在原始 75 条 canonical Backlog 内**，是 Project Owner 在 AF-102 合并后主动插入的治理性 Issue（GitHub Issue #79，理由见 `docs/20_DECISION_LOG.md` "CI-001 inserted ahead of AF-103"）。

## Problem

AF-101、AF-102 已经产生真实、可合并的代码（`src/aegisflow_core/`、`Dockerfile`、`compose.yaml`、两批 pytest 套件），但从 Phase 0 Exit 到现在的三次合并（PR #76/#77/#78）里，"测试通过"完全依赖贡献者（Codex）在 PR 描述里自报的本地命令输出，没有任何独立、自动、GitHub 原生可见的验证。`docs/25_PHASE0_EXIT_REVIEW.md` 记录的"main 分支无 Branch Protection"风险从 Phase 0 Exit 起一直未处理；AF-103 即将引入数据库迁移，是本仓库目前"改错代价最高"的一类变更。

## Objective

按 GitHub Issue #79 的 Acceptance Criteria，建立：

1. 一个在每个 PR 上自动运行的 GitHub Actions workflow，复现 AF-101/AF-102 已建立的 pytest 套件（含覆盖率门槛）；
2. 结果通过 GitHub 原生 Checks UI 可见，不需要额外工具；
3. main 分支的 Branch Protection，至少要求该 workflow 作为 Required Status Check；
4. 全程不引入 lint/typecheck 工具链、不需要真实 Secret。

## Non-Goals

明确不做：

- **不引入 `ruff`/`mypy` 等 lint/typecheck**——沿用 AF-101 决策 5、AF-102 的一致排除范围，未获人工明确扩大前不动。
- **不在 CI 里跑完整 `docker compose up` + healthcheck 集成验证**——`tests/test_docker_compose_config.py`（AF-102 已交付）本身会在 CI runner 上真实执行（GitHub Actions `ubuntu-24.04` 预装 Docker/Compose v2，不会被跳过），已经覆盖 Compose 文件的静态正确性；CI 里只新增 `docker compose build core`（见 Resolved Decisions 1），不拉起完整三服务栈、不做运行时 healthcheck 集成。
- **不推送 Docker 镜像到任何 Registry**——`docker compose build core` 只做本地构建验证，构建产物不 push、不打 Tag。
- **不做 CI 的部署/发布流水线**——`v0.0.0-docs` 等 Tag 与 Release 属于 `docs/15_RELEASE_AND_VERSIONING.md`/`docs/10_GIT_GITHUB_WORKFLOW.md` 的独立范畴，不在本 Issue 内触发。
- **不涉及 AF-507（M5 Prompt Regression Gate）**——AF-507 是评测/Prompt 回归专用的 CI 门禁，依赖 Golden Dataset（AF-501+），与本 Issue 的"通用 pytest 回归"是完全不同的两条门禁，命名上也刻意用 `CI-001` 而非借用 `AF-507` 的编号，避免混淆。
- **不修改 canonical CSV/Backlog 中 AF-103 的 `Dependencies` 字段**——`project/GITHUB_ISSUE_IMPORT.csv` 与 `docs/05_GITHUB_ISSUE_BACKLOG.md` 里 AF-103 的依赖数据继续保持 `AF-101,AF-102` 不变，不把 `CI-001` 写进这两个事实源文件，避免污染 canonical 75 条基线的依赖图（见"关键澄清"）。

## Proposed Flow

### 1. Workflow 触发与任务设计

```yaml
name: CI
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1  # v7.0.1
        with:
          persist-credentials: false
      - uses: astral-sh/setup-uv@c771a70e6277c0a99b617c7a806ffedaca235ff9  # v9.0.0
        with:
          version: "0.11.31"
          python-version: "3.12"
          enable-cache: true
          cache-dependency-glob: uv.lock
      - run: uv sync --locked
      - run: |
          uv run --locked python -m pytest \
            --cov=aegisflow_core \
            --cov-report=term-missing
      - name: Build Core container image
        env:
          APP_ENV: test
          POSTGRES_USER: ci-placeholder
          POSTGRES_PASSWORD: ci-placeholder-only
          POSTGRES_DB: aegisflow_ci
        run: docker compose build core
```

要点（含人工 Review 后的最终确定值，替代此前的占位符与开放问题）：

- 同时监听 `pull_request` 和 `push: branches: [main]`——前者是主要的 PR gate 场景，后者确保万一将来又出现一次"直接推 main"的例外（`docs/20_DECISION_LOG.md` 里已经发生过一次），也能第一时间在 main 上跑出信号，而不是完全没有反馈。
- `concurrency.group` 同时包含 `github.workflow` 与 `github.ref`——比只用 `github.ref` 更精确，避免未来仓库出现第二个 workflow 时并发组互相冲突。
- `runs-on: ubuntu-24.04`（而非泛化的 `ubuntu-latest`）：显式锁定 Runner 镜像版本，避免 GitHub 更新 `ubuntu-latest` 指向时引入不可预期的环境漂移；`timeout-minutes: 15` 防止任何意外挂起的任务无限占用 Actions 配额。
- `permissions: contents: read`——最小权限，CI 本身不需要写权限；工作流全程不引用任何 `secrets.*`。
- `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1`（对应 Release `v7.0.1`）与 `astral-sh/setup-uv@c771a70e6277c0a99b617c7a806ffedaca235ff9`（对应 Release `v9.0.0`）——均已用 `gh api repos/<owner>/<repo>/git/refs/tags/<tag>` 核验 tag 与 commit SHA 的对应关系，是完整 40 位 commit SHA 而非可变 tag，符合 `docs/09_SECURITY_BASELINE.md` 供应链要求。`persist-credentials: false` 是额外加固：checkout 后不在本地 git 配置里保留 `GITHUB_TOKEN` 凭证，缩小后续步骤（尤其是 `docker compose build` 这类会执行第三方构建逻辑的步骤）能触达的攻击面。
- `astral-sh/setup-uv` 必须显式传 `version: "0.11.31"`——不传则该 Action 可能默认安装 `uv` 的 latest 版本，与"锁定版本、可复现"的原则相悖；`python-version: "3.12"` 与已批准的 `.python-version`/`pyproject.toml` 一致；`cache-dependency-glob: uv.lock` 让依赖缓存精确按锁文件哈希失效，避免缓存陈旧。Codex 实现时需确认 `uv 0.11.31` 能正确读取仓库内 `uv.lock`（`revision = 3` 格式）；如遇兼容性问题，允许升级到另一个具体版本号，但必须保持"显式 pin 某个确定版本"，不得退化为不传版本号或传 `latest`。
- `uv sync --locked`：与 `Dockerfile` 的既有 `--locked` 用法一致，锁文件与 `pyproject.toml` 不一致时直接失败，不静默重新解析。
- `uv run --locked python -m pytest --cov=aegisflow_core --cov-report=term-missing`：显式启用覆盖率采集，触发 `pyproject.toml` 里已经存在但此前从未被实际执行路径命中的 `fail_under = 90` 门槛——覆盖率不达标会让 `pytest` 以非 0 退出，CI 直接标红。命令前缀 `--locked` 是双重保险，确保这一步也不会意外触发依赖重新解析。
- `docker compose build core`（Open Question 1 的最终答复：**采纳**，只 `build` 不 `up`）——见"与 AF-102 的关系"一节的更新说明。

### 2. 与 AF-102 `test_docker_compose_config.py` 及新增 `docker compose build core` 的关系

`test_docker_compose_config.py` 已经在 AF-102 中交付，内容是对 `compose.yaml`/`Dockerfile`/`.dockerignore`/`.env.example` 的静态护栏检查（见 AF-102 Test Plan Evidence："静态与回归：30 passed"）。GitHub Actions `ubuntu-24.04` runner 预装 Docker Engine 与 Compose v2 插件，所以这个测试在 CI 里会**真实执行**（不会因为"检测不到 docker"而跳过）。

在此基础上，本 Issue 额外新增一个独立步骤 `docker compose build core`（Open Question 1 已确定采纳）：只构建 Core 镜像，**不 `up`**、不拉起 PostgreSQL/Redis、不做端到端 healthcheck 集成验证。理由：

- 能发现 `Dockerfile`、`uv.lock`、打包相关的错误（例如镜像构建阶段的依赖解析失败），这类问题是 `test_docker_compose_config.py` 的静态检查覆盖不到的；
- 成本合理——只构建不运行，不引入端口占用、服务间时序等会导致 CI 偶发失败（flaky）的变量；
- 三服务真实运行的集成验证（`docker compose up` + healthcheck）暂时保留在本地人工验证范畴（AF-102 Test Plan 已覆盖），不引入 CI，降低 CI 本身的波动性。

### 3. Branch Protection 配置（与 workflow 文件分开处理，含账号条件修正）

Branch Protection 是仓库设置而非代码文件。为让 CI-001 自身也通过新 Gate，配置时机确定为：实现 PR 的 `CI / test` 已真实出现并最终转绿之后、Human Merge 之前。配置前必须再次向 Project Owner 展示精确规则并获得明确授权。

**账号条件澄清（人工已确认）**：本仓库是 Private，目前只有一位协作者 `KinguYume-G`，没有第二位可信 Human Reviewer 可加入。如果 Branch Protection 要求"至少 1 个 approving review"，PR 作者无法批准自己的 PR，会导致没有任何人能完成正式 Approval、所有 PR 永久卡死在 Review 阶段。因此采用**过渡规则**（而非放弃 Branch Protection）：

- **强制要求走 PR**（不允许直接 push main）；
- **强制要求 `CI / test` Required Status Check 通过**；
- **强制要求 Review conversation 全部 resolved**；
- **禁止 force push、禁止删除 main 分支**；
- **`required_approving_review_count` 暂时设为 `0`**（因为没有第二位可信 Reviewer，这一项在数量上无法立即满足 ≥1 的目标）；
- 即便如此，**人工 Review / Human Merge 仍按 `AGENTS.md`/`docs/10_GIT_GITHUB_WORKFLOW.md` 既有流程执行**——approval 数量为 0 是 GitHub 机制层面的临时妥协，不是"可以不 Review"的许可，你在合并前仍需要实际读过 PR 内容；
- 在治理文档中明确记录"正式 1 票 Approval 要求，待第二位可信 Reviewer 加入仓库后启用"（见 Documentation Updates）。

**执行顺序**（细化自此前版本，修正为 6 步）：

1. Codex 提交 `.github/workflows/ci.yml` 的 PR（`infra/CI-001-foundational-ci` 分支，需从最新 `origin/main` 新建，见 Codex 清单第 1 项）。
2. 在同一 PR 里完成"红灯 → 绿灯"验证（见配套 Test Plan）。
3. 确认 Check `CI / test` 已经在该 PR 的 Checks 列表中真实出现过（不管当前是红是绿，只要出现过这个 context 名字，GitHub 才允许把它设为 Required）。
4. 你审阅并明确批准本节列出的具体 Branch Protection 规则（含 `required_approving_review_count: 0` 的过渡设定）。
5. 由 Repository Governance Engineer 用 `gh api` 配置 Branch Protection（API 配置比网页手动点击更精确、可复核、有执行记录可追溯）；仅限本 PR 的 workflow 已最终转绿、且你已完成第 4 步的具体规则确认之后执行。
6. 之后才由你 Human Review + Human Merge 这个 CI-001 PR 本身——这样 CI-001 自己也是通过它刚刚建立起来的受保护流程进入 main，形成闭环，而不是在保护生效前抢跑合并。

## State Ownership / External Side Effects / Idempotency

- Workflow 运行不持久化业务状态，不部署、不推镜像、不写外部系统；每次 GitHub-hosted runner 运行相互独立、可重复执行。
- Branch Protection 是本 Issue 唯一的外部治理状态写入，事实源为 GitHub `main` 分支保护配置，风险级别 L3。写入前必须读取当前状态、展示精确 payload 并取得 Project Owner 明确授权；写入后必须通过 API 回读核验。
- Branch Protection 使用同一完整配置执行 `PUT`，重复执行得到相同规则，属于幂等设置操作。回滚必须同步移除或调整 Required Check，避免 workflow 被撤销后 main 永久无法合并。

## Failure Modes

| 失败场景 | 预期行为 |
|---|---|
| `uv.lock` 与 `pyproject.toml` 不一致 | `uv sync --locked` 直接失败，CI 标红，退出码非 0 |
| 任一 pytest 用例失败 | `pytest` 非 0 退出，CI 标红；不允许通过重跑掩盖，`docs/08_TEST_STRATEGY.md` Flaky Test 规则同样适用于 CI |
| 覆盖率低于 90%（`fail_under`） | `pytest --cov` 非 0 退出，CI 标红，即使所有用例本身通过 |
| Actions 平台自身故障（如 runner 不可用） | 属于 GitHub 平台可用性问题，不是本 Issue 设计范畴；PR 应等待重跑，不得因此绕过 Required Status Check |

## Security Impact

- Workflow 本身 Risk Level：**L1/L2**（只读 checkout + 跑测试 + 本地构建镜像，`permissions: contents: read`，无 Secret、无外部写操作、无镜像 push）。
- **Branch Protection 配置**本身是更高影响面的治理动作（影响所有未来 PR 能否合并），归类为 **L3**（需要你在执行前逐条确认具体规则），不与 workflow 文件本身的 L1/L2 混为一谈——执行方式见"Branch Protection 配置"一节的 6 步流程。
- **`required_approving_review_count: 0` 的过渡状态本身是一项需要持续追踪的安全态势**：在没有第二位可信 Reviewer 之前，任何能推送分支的人（目前只有 `KinguYume-G` 一人）在 CI 通过后即可合并自己的 PR，Review 环节退化为"自我核查"而非"他人把关"。这是账号条件下的必要妥协，不是理想状态；一旦有第二位可信 Reviewer 加入仓库，应立即把 `required_approving_review_count` 改回 `1`，并在 `docs/10_GIT_GITHUB_WORKFLOW.md` 同步更新。
- 供应链：新增两个外部 Action 依赖（`actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1`、`astral-sh/setup-uv@c771a70e6277c0a99b617c7a806ffedaca235ff9`），均已用完整 40 位 commit SHA pin 并核验与对应 Release tag 一致，符合 `docs/09_SECURITY_BASELINE.md`"固定 GitHub Action 版本"要求。
- 无真实 Secret；CI 不需要访问任何 `.env` 中列出的凭证类配置；workflow 不引用任何 `secrets.*`。
- **明确延后的安全项**：依赖/Secret 泄露的自动化扫描（例如 `uv` 生态的漏洞审计工具、GitHub Secret Scanning、Dependabot alerts）**不在本 Issue 范围内**，留作独立的后续安全加固 Issue（不占用本次"foundational"CI 的最小范围）。

## Rollback

- 删除或禁用 `.github/workflows/ci.yml` 即可让新 PR 不再触发该 workflow；若 Branch Protection 已配置且此时回滚 workflow 文件，需要**同时**解除或调整 Required Status Check 设置，否则所有新 PR 会因为"要求的 Check 永远不会出现"而被永久阻塞在合并前——这是本 Issue 唯一需要特别小心的回滚耦合点，必须在 Rollback 步骤里显式包含"检查并调整 Branch Protection"这一步，不能只 revert 代码文件。
