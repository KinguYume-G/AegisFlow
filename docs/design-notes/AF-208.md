# Design Note — AF-208 Implement GitHub draft pull request tool

> 状态：**Draft v2**，等待人工最终 Review。依赖 AF-202、AF-205、AF-206、AF-207（均为 Draft，先于本 Issue 批准）。Codex 在获得批准前不得实现。v2 行为以共享契约 §0A 为准。
> 前提文档：`docs/design-notes/M2-SHARED-CONTRACTS.md`（第 10、13 节）。GitHub #27。

## Draft v2 implementation contract

- Create Draft PR 固定为 L3；不存在 L1/L2 自动写入路径。
- 参数必须包含经 `ApprovalAuthorizer` 验证的 `WriteAuthorization`，绑定 tenant/run/step/repository/base SHA/patch digest。非空 UUID 不构成授权。
- 输入为结构化 `FileChange` 集合。使用 Git Data API 创建 blobs/tree/commit，再以 expected base SHA 条件更新 ref；不得把 unified patch 当成 GitHub 原子写 API。
- 在任何远端写入前获取原子幂等 claim，并结合 head/Marker reconciliation；`InProgress` 不执行，`Reuse` 直接返回。部分失败只能恢复同一 Marker 的分支，不能创建第二个 PR。

## Problem

Reviewer 批准后的改动需要真正落地为 GitHub 上的 Branch/Commit/Draft PR；这是 Gate 1B 唯一真正对外部系统产生写副作用的动作（L3 风险），必须有授权前置检查、Scope 限定、AegisFlow Marker 与幂等保护，而此时 AF-209 的 Idempotency Ledger 表尚未交付。

## Objective

按 Issue #27 AC 实现异步 `create_draft_pull_request(...)`：数据库验证的 `WriteAuthorization`、固定 Scope/Marker、写入前原子幂等 claim、远端 reconciliation，以及 Git Data API 的结构化文件写入。

## Non-Goals

- 不在本 Issue 建 Ledger 表（AF-209 范围），但写路径从第一版就要求显式注入非 NoOp 的 `IdempotencyGuard`。
- 不做 Merge（只创建 Draft PR，`09_SECURITY_BASELINE.md` L4 Merge 是另一个更高风险等级，超出 DeliveryPack 自动化范围）。
- 不做 Review Comment/Approve GitHub 原生审查操作（AegisFlow 自己的 Reviewer Agent 已经在 AF-206 完成审批判断，本 Issue 只负责把结果落地为 PR）。
- 不做 Webhook 触发（AF-201 范围）。

## Affected Modules

- 新增 `gateway/github/pull_request.py`（异步写协议、`WriteAuthorization`、`FileChange`、`create_draft_pull_request`、结果与结构化错误）。
- 新增 `tests/gateway/github/test_pull_request.py`。
- 修改 `docs/21_TRACEABILITY_MATRIX.md`。
- 不修改 `gateway/github/auth.py`/`webhook.py`/`read_tools.py`（AF-201/202 冻结）。

## Proposed Flow

### Schema 与协议（`gateway/github/pull_request.py`）

```text
class DraftPullRequestResult(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)
    schema_version: Literal[1] = 1
    pull_request_url: str
    pull_request_number: int
    branch_name: str
    reused_existing: bool   # True 表示命中幂等检查复用了既有 PR，未真正新建

class FileChange(BaseModel):
    path: str
    operation: Literal["add", "update", "delete"]
    content: bytes | None

class WriteAuthorization(BaseModel):
    approval_id: UUID
    tenant_id: UUID
    run_id: UUID
    step_id: UUID
    repository_target: RepositoryTarget
    base_sha: str
    content_digest: str
```

### `create_draft_pull_request`

```text
async def create_draft_pull_request(
    *, github_client: GitHubWriteClient, read_client: GitHubReadClient,
    changes: tuple[FileChange, ...], authorization: WriteAuthorization,
    approval_authorizer: ApprovalAuthorizer, idempotency_guard: IdempotencyGuard,
) -> DraftPullRequestResult:
    await approval_authorizer.verify(authorization, digest(changes))

    command = IdempotentCommand.from_authorized_changes(authorization, changes)
    claim = await idempotency_guard.begin(command)
    if isinstance(claim, Reuse): return _result_from_reference(claim.result_reference)
    if isinstance(claim, InProgress): raise IdempotencyInProgressError(claim.retry_after_seconds)
    if isinstance(claim, FinalFailure): raise IdempotencyFinalFailureError(claim.reason)

    branch_name = f"aegisflow/run-{authorization.run_id}"
    marker = marker_for(command)

    existing = await read_client.find_pull_request_by_head_or_marker(authorization.repository_target, branch_name, marker)
    if existing is not None:
        await idempotency_guard.complete(claim.claim_token, existing.url)
        return _result_from_existing(existing, reused_existing=True)

    commit = await github_client.create_commit_from_changes(
        target=authorization.repository_target, expected_base_sha=authorization.base_sha,
        branch_name=branch_name, changes=changes, author=_BOT_AUTHOR,
    )  # blobs → tree → commit → conditional ref
    pr = await github_client.open_draft_pull_request(authorization.repository_target, branch_name, marker)
    await idempotency_guard.complete(claim.claim_token, pr.url)
    return _result(pr, branch_name, commit.sha)
```

`idempotency_key` 的具体拼接格式**只在本 Issue 内部使用**（远端 Marker 需要人类可读、AF-209 的 Ledger `idempotency_key` 是独立 sha256 摘要，两者不必字面相同——AF-209 在实现时把这个字符串作为其 `canonical_arguments_hash` 的输入之一即可，具体对齐方式见 AF-209 Design Note）。

### `GitHubWriteClient`（新增最小写客户端，与 AF-202 的 `GitHubReadClient` 并列但独立）

复用 AF-201 的 token provider；只暴露创建 blob/tree/commit、conditional ref 与 Draft PR 的窄异步方法，不做通用 API 转发。错误映射复用 AF-202 定义。

## State Ownership / External Side Effects / Idempotency

- **State Ownership**：持久状态由 AF-209 Ledger 所有；AF-208 必须取得其原子 claim 才能写 GitHub。
- **External Side Effects**：GitHub 分支创建、Commit、Draft PR 创建——本 Bundle 内唯一的真实外部写副作用。
- **Idempotency**：本地原子 claim 与远端 Marker reconciliation 同时必需；没有 Guard 时 fail closed。

## Failure Modes

| 场景 | 预期行为 |
|---|---|
| 缺失、伪造、过期或绑定不匹配的 `WriteAuthorization` | `MissingApprovalError`，不触碰 GitHub |
| 远端已存在同 Marker 的 PR | 复用，`reused_existing=True`，不重复创建 |
| Git Data API 任一步骤失败 | claim 标为 retryable；下一次调用 reconciliation 同一 Marker 分支和 expected base SHA，不创建第二个 PR |
| GitHub API 429/5xx | 复用 AF-202 的错误类型向上抛出，不在本函数内重试（重试策略是调用方/未来 Temporal Activity 的职责,`18_RELIABILITY_PLAN.md` Retry Ownership 分层原则） |

## Security Impact

Risk Level L3（"Create Draft PR"，`09_SECURITY_BASELINE.md` 明确要求 Reviewer approval）。§10.1 的授权前置检查是本 Issue 最核心的安全属性,必须有专门的负向测试。`19_THREAT_MODEL.md` 的 `Tool Abuse` 通过"固定 Scope（分支命名/Author）+ 不做任意 API 转发"缓解。
