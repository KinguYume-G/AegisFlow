# Design Note — AF-201 Register GitHub App and verify webhook signature

> 状态：**Draft v2**，等待人工最终 Review。依赖 AF-102（已合并）。Codex 在获得批准前不得实现，也不得创建 PR。v2 行为以共享契约 §0A 为准。
> 前提文档：`docs/design-notes/M2-SHARED-CONTRACTS.md`（第 2、3、4.1、13 节）。GitHub #20。

## Draft v2 implementation contract

- 只接收已验签且 Schema 合法的 `repository_dispatch`；校验与 dispatch 全异步。
- 不伪造 webhook 事件时间。以 `(installation_id, X-GitHub-Delivery)` 进入 10 分钟有界 replay cache；重复 delivery 返回 409、写 `duplicate_delivery` 拒绝审计、不得触发任何下游动作。
- cache 有明确容量上限与单调时钟；AF-209 负责以持久 Ledger 替换它，AF-201 的端点必须预留异步 replay guard 注入缝。
- GitHub App JWT 使用 `PyJWT[crypto]`/`cryptography`，Installation Token 与私钥永不进入日志、Trace 或 Audit payload。

## Problem

DeliveryPack 需要一个可信的、经过签名校验的 GitHub 事件入口，作为 Gate 1B 的触发点；在此之前仓库完全没有对外 Webhook 端点，也没有任何 GitHub App 身份基础设施。

## Objective

按 Issue #20 AC（"签名、时间窗口、防重放和失败审计测试通过"），建立：

1. `InstallationTokenProvider`（GitHub App JWT 签名 → Installation Token 获取与缓存）；
2. `POST /webhooks/github` 端点，实现 SHARED-CONTRACTS §3.1 的四步固定校验顺序；
3. Bootstrap Tenant/Workflow 的 get-or-create 助手（`control_plane/bootstrap.py`），供本 Issue 与后续 M2 Issue 复用；
4. 每次校验结果写入 `audit_events`（通过与拒绝均记录）。

## Non-Goals

- 不处理任何具体 GitHub 事件的业务语义（不触发 Intake、不创建 Run/Step）——本 Issue 只做"身份 + 签名 + 时间窗口 + 结构 + 审计"，触发下游流程是 AF-210 图组装的职责。
- 不实现跨请求持久化去重（AF-209 职责，见 SHARED-CONTRACTS §3.1 第 4 点、§11.3）。
- 不做多租户路由/多 Installation 支持（M2 固定单一 Bootstrap Tenant + 单一 Installation）。
- 不引入 Temporal、不做真实模型调用。

## Affected Modules

- 新增 `gateway/github/__init__.py`、`auth.py`（`InstallationTokenProvider`）、`webhook.py`（校验管道 + FastAPI 路由）。
- 新增 `control_plane/bootstrap.py`（`get_or_create_bootstrap_tenant`/`get_or_create_bootstrap_workflow`）。
- 修改 `app.py`：挂载 `webhooks/github` 路由。
- 修改 `settings.py`：新增 `github_app_id`/`github_app_private_key`/`github_app_webhook_secret`/`github_app_installation_id`/`aegisflow_bootstrap_tenant_slug`（全部可选，未配置时该子系统不可用，遵循 AF-109 的 all-or-none 校验风格：GitHub App 四项配置必须全部存在或全部缺失，缺失时 `/webhooks/github` 返回 503 而非 500）。
- 新增 `tests/gateway/github/`、`tests/control_plane/test_bootstrap.py`。
- 修改 `docs/21_TRACEABILITY_MATRIX.md`。

## Proposed Flow

### `InstallationTokenProvider`（`gateway/github/auth.py`）

```text
class InstallationToken(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)
    token: str
    expires_at: datetime

class GitHubAppAuthError(RuntimeError): ...

class InstallationTokenProvider:
    def __init__(self, app_id: str, private_key_pem: str, installation_id: str, clock: Clock): ...

    def get_token(self) -> InstallationToken:
        # 缓存的 token 若在 clock.now() + 60s 缓冲期内仍未过期则直接复用；
        # 否则用 app_id + private_key_pem 签一个新的 App JWT（RS256，exp <= 10 分钟，
        # 具体 PyJWT/cryptography 用法由 Codex 实现时核实），
        # 用该 JWT 调用 GitHub "Create an installation access token" 端点换取新 Token。
        ...
```

`private_key_pem` 只在内存中持有，永不写日志/Trace/异常消息；`GitHubAppAuthError` 的 `str()` 不包含私钥或已获取的 Token 值。

### Webhook 校验管道（`gateway/github/webhook.py`）

```text
class WebhookRejectionReason(StrEnum):
    INVALID_SIGNATURE = "invalid_signature"
    SCHEMA_REJECTED = "schema_rejected"
    DUPLICATE_DELIVERY = "duplicate_delivery"

class WebhookVerificationResult(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)
    accepted: bool
    delivery_id: str
    event: str | None
    rejection_reason: WebhookRejectionReason | None

def verify_webhook(
    *, raw_body: bytes, signature_header: str | None, event_header: str | None,
    delivery_id_header: str | None, webhook_secret: str,
    allowed_events: frozenset[str],
) -> WebhookVerificationResult:
    # 固定顺序：签名 → 结构。通过后由异步 ReplayGuard 原子 claim delivery。
    ...
```

FastAPI 路由 `POST /webhooks/github` 调用 `verify_webhook(...)`，再调用异步 `ReplayGuard.claim(installation_id, delivery_id)`。无论 accepted 与否都写一行 `AuditEvent`（`actor="github_webhook"`、`action="verify"`、`resource_type="webhook_delivery"`、`resource_id=delivery_id`、`decision="allow"|"deny"`、`reason`），`tenant_id` 取 Bootstrap Tenant。拒绝时返回 `401`（签名）、`400`（结构）或 `409`（重复 delivery），响应体不回显 Payload。首次合法请求返回 `202 {"status": "accepted"}`；AF-201 只调用注入的 no-op dispatch，AF-209 将其替换为持久化 dispatch。

## State Ownership / External Side Effects / Idempotency

- **State Ownership**：`audit_events`/`tenants`/`workflows` 均是 AF-103 已定义的 Core Domain PostgreSQL 表；本 Issue 是它们的第一个真实写入方（M1 从未写入过）。
- **External Side Effects**：调用 GitHub "Create an installation access token" API（读操作性质，不改变 GitHub 侧任何资源状态）。
- **Idempotency**：`verify_webhook` 本身是纯函数，无副作用；审计写入允许重复（每次校验都写一行,不去重——去重是 AF-209 职责）；Bootstrap 助手是 get-or-create 意义下的幂等。

## Failure Modes

| 场景 | 预期行为 |
|---|---|
| 签名不匹配 | `401`，`AuditEvent(reason="invalid_signature")` |
| 重复 delivery | `409`，`AuditEvent(reason="duplicate_delivery")`，dispatch 次数不增加 |
| `event`/Payload 结构不符 | `400`，`AuditEvent(reason="schema_rejected")` |
| GitHub App 四项配置部分缺失 | 启动时/请求时 `ConfigurationError`（镜像 AF-109 的 all-or-none 校验），`/webhooks/github` 返回 `503` |
| GitHub Installation Token 获取失败（网络/GitHub 5xx） | `GitHubAppAuthError`，不影响 Webhook 校验路径本身（Token 只在需要回调 GitHub 时才获取，签名校验不需要它） |
| Bootstrap 助手并发创建冲突 | 唯一约束冲突后回查成功返回已存在行，不抛异常 |

## Security Impact

Risk Level L1（`09_SECURITY_BASELINE.md`：接收/校验外部输入,不产生写副作用）。这是仓库第一个暴露给公网的入口，威胁模型 `19_THREAT_MODEL.md` 的"Webhook Forgery/Replay"直接映射到本 Issue：signature（§3.1.1）、timestamp（§3.1.2）、delivery ID（§3.1.4，窗口级，跨请求精确去重留给 AF-209）均已覆盖；`Secret Leakage` 威胁通过"私钥/Token 值不进日志"覆盖。
