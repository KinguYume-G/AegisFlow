## Problem

Phase 0 已经人工确认结束（AF-000–AF-008 全部 Closed / `status:verified`，PR #76 已由仓库所有者 Human Merge）。AF-101 的唯一依赖 AF-008 已关闭。仓库当前没有任何应用代码——`aegisflow_core/` 模块边界目前只存在于 `docs/02_ARCHITECTURE.md` 的文字描述和 Mermaid 图里，没有落地成真实的 Python 包结构，也没有任何可运行、可测试的最小 FastAPI 应用。M1 后续所有 Issue（AF-102 Docker Compose、AF-103 领域模型、AF-104–107 六个 Agent 契约……）都需要一个已经存在、边界清晰、可 import、可启动、可测试的骨架作为落点。

## Objective

按 `docs/05_GITHUB_ISSUE_BACKLOG.md` 中 AF-101 的原始 Acceptance Criteria："模块目录存在；只有骨架接口；测试先行"，建立：

1. 与 `docs/02_ARCHITECTURE.md`／`docs/DESIGN_BLUEPRINT.md` 一致的 `aegisflow_core` 模块化单体目录骨架（`control_plane / runtime / gateway / models / evaluation / packs/delivery`）；
2. 一个可以真实启动的最小 FastAPI 应用；
3. 一个稳定的最小 health contract，供 AF-102 的 Docker healthcheck 直接消费；
4. 一个最小、可测试、fail-fast 的配置加载骨架；
5. 与之匹配的测试先行的测试套件（见配套 `docs/test-plans/AF-101.md`）。

## Non-Goals

明确不做（越界即为范围外，需拆到对应后续 Issue）：

- 不实现任何业务逻辑、Agent、LangGraph 图、Temporal Workflow、RAG、MCP、RBAC、前端（AF-104 及以后）。
- 不接入 PostgreSQL、Redis、Temporal、GitHub App、LiteLLM、Langfuse、OTel 等外部系统，不做任何真实连接测试（AF-102/103/109/201/301/310/508 等）。
- 不写 Docker Compose 或任何容器编排文件（AF-102）。
- 不定义领域模型或数据库迁移（AF-103）。
- 不提前创建 `packs/delivery/{intake,clarifier,context,planner,executor,reviewer}` 六个 Agent 子目录——这些属于 AF-104–107，本 Issue 只建到 `packs/delivery/` 这一层作为边界占位。
- 不引入 `Makefile` 或 `ruff/mypy` 等 lint/format/typecheck 工具链配置；Project Owner 已确认这些工具不属于 AF-101。
- 不配置 CI（GitHub Actions）。

## Proposed Flow

### 1. 目录设计（FastAPI 模块化单体）

采用已经人工批准的 **src-layout**（`src/aegisflow_core/`，而非仓库根目录直接放包）。这样可避免未安装包时被本地目录意外 shadow 导入，并让 `pyproject.toml` 以标准方式识别包边界。

```text
src/
└── aegisflow_core/
    ├── __init__.py
    ├── main.py                  # ASGI 入口：uvicorn aegisflow_core.main:app
    ├── app.py                   # create_app() 工厂函数
    ├── settings.py              # 最小配置加载骨架
    ├── logging.py               # 结构化日志基础配置
    ├── health/
    │   ├── __init__.py
    │   └── router.py            # GET /health
    ├── control_plane/
    │   └── __init__.py          # 边界占位，docstring 注明归属 AF-401/402/403/405/406
    ├── runtime/
    │   └── __init__.py          # 边界占位，docstring 注明归属 AF-104-107/301-309
    ├── gateway/
    │   └── __init__.py          # 边界占位，docstring 注明归属 AF-201-211/406/407
    ├── models/
    │   └── __init__.py          # 边界占位，docstring 注明归属 AF-310/311
    ├── evaluation/
    │   └── __init__.py          # 边界占位，docstring 注明归属 AF-501-511
    └── packs/
        ├── __init__.py
        └── delivery/
            └── __init__.py      # 边界占位，docstring 注明归属 AF-104-108（六个 Agent）

tests/
├── __init__.py
├── conftest.py                  # 共享 fixture（httpx AsyncClient + ASGI transport）
├── test_health.py               # health contract 测试
├── test_app_startup.py          # 应用启动测试（正常 + 配置缺失/错误）
├── test_settings.py             # settings 加载与校验测试
└── test_module_boundaries.py    # 模块导入边界静态检查测试
```

`control_plane/runtime/gateway/models/evaluation` 只到第一层（不预建 `tenants/identity/rbac/...` 等二级子目录）——那些属于各自的后续 Issue（AF-401 起），提前建空目录会造成"未来 Issue 落地时目录已存在但无人负责验证其正确性"的歧义，违反"最小实现，不顺手重构"。

### 2. 模块职责与依赖方向

严格执行 `docs/06_DEVELOPER_GUIDE.md` 的依赖方向：

```text
packs/delivery
    ↓（依赖）
runtime / control_plane 的接口（尚未定义，本 Issue 不产出接口，只留包边界）
    ↓
gateway / models / evaluation
    ↓
infrastructure adapters（尚不存在）
```

本 Issue 阶段，五个边界包（`control_plane/runtime/gateway/models/evaluation`）和 `packs/delivery` 内部**没有任何代码**，只有 `__init__.py`；因此当前实际不存在依赖违反的可能——但"模块导入边界测试"（见 Test Plan）要作为**静态护栏**现在就写好并通过，防止未来 Issue 在这些包里意外 `import fastapi`、`import httpx` 或任何 Model Provider SDK，破坏"Domain 不依赖 Web Framework/MCP SDK/Model Provider SDK"的铁律。`app.py`／`main.py`／`health/` 可以依赖 `fastapi`，因为它们属于"应用组装层"而非 Domain。

### 3. 最小应用启动方式

- `aegisflow_core.app:create_app() -> FastAPI`：工厂函数，负责实例化 `FastAPI()`、挂载 `health` 路由、注册全局异常处理器（见"错误处理原则"）、调用 `settings.get_settings()` 完成一次 fail-fast 配置校验。
- `aegisflow_core.main:app`：模块级变量 `app = create_app()`，作为 ASGI 目标。
- 本地开发启动命令：`APP_ENV=development uv run uvicorn aegisflow_core.main:app --reload`（Windows PowerShell 先执行 `$env:APP_ENV='development'`）。`uv sync` 会通过已批准的 hatchling build backend 安装 src-layout 包，无需手工设置 `PYTHONPATH`。
- 启动失败即视为设计正确：若 `APP_ENV` 缺失或不在允许值内，`create_app()`（经由 `settings.get_settings()`）必须在应用对象构造阶段直接抛出异常并退出非 0，而不是启动后在请求时才报错——这是"配置缺失和错误配置测试"要验证的核心行为。

### 4. 最小 health endpoint 契约

- 路径：`GET /health`
- 成功响应：HTTP `200`，JSON Body：

  ```json
  {"status": "ok", "service": "aegisflow-core"}
  ```

- 本 Issue **不做**任何依赖探活（不 ping PostgreSQL/Redis/Temporal）——那是"deep health check"，属于 AF-102（Docker Compose healthcheck 落地时）或更晚的可观测性 Issue，届时可能新增 `GET /health/ready` 或扩展本响应体，但**不得**修改 `/health` 现有响应体的既有字段语义（`status`/`service` 字段一旦发布即视为契约，向后兼容扩展用新增字段或新增路径，不做破坏性变更）。
- 这一条是本 Design Note 里对 AF-102 最关键的承诺：AF-102 的 Docker Compose healthcheck 会直接依赖这个契约，改动前必须重新过 Design Review。

### 5. 配置加载方案

- 新增 `aegisflow_core/settings.py`，暴露 `get_settings() -> Settings`（建议用 `functools.lru_cache` 做进程内单例，避免重复读取环境变量）。
- 本 Issue 阶段**只加载并校验两个字段**：
  - `APP_ENV`：必需，取值必须是 `.env.example` 中已声明的 `development|test|production` 三者之一；缺失或非法值 → 启动时抛出明确异常（例如 `RuntimeError` 或自定义 `ConfigurationError`），阻止应用启动。
  - `APP_BASE_URL`：可选，允许为空（当前无实际用途，只做占位透传，避免未来 Issue 再改一次 Settings 结构）。
- **明确不读取** `.env.example` 中 DATABASE_URL/REDIS_URL/TEMPORAL_*/OIDC_*/GITHUB_*/LITELLM_*/LANGFUSE_*/OTEL_*/SANDBOX_*/ENCRYPTION_KEY_REFERENCE 等分组——提前读取但不使用这些变量，会造成"看起来已经支持数据库/Redis/Temporal"的错觉，与 AF-101"只有骨架接口"的验收标准冲突，也会在 AF-102/103/201/301/310 等 Issue 各自引入这些配置时产生重复设计决策。这些字段何时被 `settings.py` 正式消费，由各自的后续 Issue 的 Design Note 决定。
- 使用已批准的纯标准库 `os.environ` 方案，不引入 `pydantic-settings`。

### 6. 错误处理原则

- 挂载一个全局异常处理器骨架（FastAPI `exception_handler`），把未捕获异常统一转换成结构化 JSON 错误信封：

  ```json
  {"error": {"code": "internal_error", "message": "<safe, non-sensitive message>"}}
  ```

- 响应体**不得**包含堆栈跟踪、内部路径或异常的 `repr()`——与 `docs/09_SECURITY_BASELINE.md` 的"Structured Output"默认策略、以及 `AGENTS.md`"Secret 不进入 Prompt、Trace 或日志"的精神一致（虽然本 Issue 尚无 Secret 概念，但异常处理约定从第一天就要正确，避免后续 Issue 在此基础上继续暴露内部细节）。
- FastAPI 默认的 422 请求校验错误，本 Issue 暂不强制统一改写成上面的信封格式（因为目前唯一的路由 `/health` 没有请求体/参数可校验）；是否统一改写留给第一个真正带请求体的 Issue（例如 AF-104 Intake）处理，避免本 Issue 过度设计。
- 不定义任何领域异常类型（`DomainError` 等）——目前没有领域逻辑，提前定义异常层级容易在后续 Issue 里被推翻重做。

### 7. 日志基础约定

- 使用标准库 `logging`，在 `aegisflow_core/logging.py` 里提供 `configure_logging() -> None`，输出到 `stdout`，格式为结构化 JSON（字段至少含 `timestamp`/`level`/`logger`/`message`），便于未来接入容器化环境和日志采集。
- 预留（但暂不填充）`trace_id` 字段位——现在不接 OTel/Langfuse（AF-109/AF-508），但提前约定字段名，避免那两个 Issue 落地时要做一次破坏性重命名。
- 不记录请求体、环境变量值或任何可能的 Secret；这是约定和 Code Review 检查项，本 Issue 没有可记录 Secret 的代码路径（`/health` 无输入），但约定要写进代码注释/docstring，供后续 Issue 遵守。
- `create_app()` 在最开始调用一次 `configure_logging()`。

## State Ownership

本 Issue 不产生、不持有、不读写任何持久状态（无 PostgreSQL、Redis、Temporal、LangGraph checkpoint）。`docs/02_ARCHITECTURE.md` 的 State Ownership 表在此 Issue 范围内没有条目适用。

## External Side Effects

无。本 Issue 不发起任何出站网络调用（不连接 GitHub、Model Provider、Langfuse、OTel Collector 等），因此无需幂等设计。

## Idempotency

不适用（无外部副作用）。`GET /health` 天然幂等（只读、无状态）。

## Failure Modes

| 失败场景 | 预期行为 |
|---|---|
| `APP_ENV` 缺失 | 应用构造阶段（`create_app()`／`settings.get_settings()`）抛出异常，进程以非 0 退出，不进入"看起来在运行但配置错误"的状态 |
| `APP_ENV` 值非法（不在 development/test/production 内） | 同上，fail fast |
| `/health` 请求异常路径（如错误的 HTTP method） | 走 FastAPI 默认路由匹配失败逻辑（405/404），本 Issue 不额外定制 |
| 未捕获的服务器内部异常（理论上此 Issue 内没有代码路径会触发） | 全局异常处理器兜底，返回结构化 500，不泄漏堆栈 |

## Security Impact

- Risk Level：**L1/L2**（`docs/09_SECURITY_BASELINE.md`）——只读代码骨架、跑测试、临时分支编辑，Auto 或 Auto+Audit，不触发强制 Security Reviewer 审批门槛（L3 起才需要）。
- 无认证、无授权、无租户概念、无 Secret 使用——`.env.example` 中与安全相关的字段本 Issue 均不读取（见"配置加载方案"）。
- 无外部输入面（`/health` 无请求参数），无注入面、无越权面。
- 全局异常处理器本身是一项正向安全措施（防止未来 Issue 无意中把内部细节泄漏到响应体），在此登记以便 `docs/19_THREAT_MODEL.md` 未来引用。
- 供应链：本 Issue 会新增 Python 依赖（至少 `fastapi`、一个 ASGI server 如 `uvicorn`、测试用 `pytest` 与 `httpx`）。这些依赖已经被 `docs/adr/0001-modular-monolith.md` 和 `docs/02_ARCHITECTURE.md` 隐式批准（FastAPI 是既定技术选型，不是本 Issue 新引入的架构决策），但**具体版本锁定方式**（lockfile 工具）仍是 Open Question，需人工确认后 Codex 才能落地 `pyproject.toml`。
