## Problem

`docs/02_ARCHITECTURE.md` 定义了 State Ownership 铁律——"Tenant、RBAC、版本、审批事实"归 PostgreSQL/Core Domain 所有，"审计只追加"——但目前仓库里没有任何数据库 Schema、没有 ORM、没有迁移工具，Core 应用（AF-101）甚至不读取 `DATABASE_URL`。AF-102 已经把 PostgreSQL 容器接进了本地 Compose 编排，但明确排除了"给 Core 接入真实 DB 客户端"（见 AF-102 Design Note Non-Goals）。`docs/20_DECISION_LOG.md`"Open"一节把"ORM/migration"列为必须通过 Issue/ADR 决定、目前尚未决定的事项。AF-104 起的六个 Agent、AF-108 的 HITL、AF-207 的 Policy Gate、AF-305 的审批 Signal，全部需要在一个已经存在的 Tenant/Workflow/Run/Step/Approval/Audit 持久化基础上才能开始设计。

## Objective

按 GitHub Issue #12 的 Acceptance Criteria（"模型有 tenant_id；版本不可覆盖；迁移测试通过"），建立：

1. Tenant、Workflow、Run、Step、Approval、Audit 六张初始表的 ORM 模型，且所有子表通过**租户复合外键**引用父表，数据库物理拒绝跨租户关联；
2. 一套可重复执行、可回滚一步、**在 CI 中自动验证**的数据库迁移；
3. 数据库层面（而非仅靠应用代码自觉）强制的"Workflow 版本不可覆盖"（允许受控的 `status` 流转）与"审计只追加"约束；
4. Core 应用读取 `DATABASE_URL` 并能建立数据库连接（异步引擎/会话），但不在本 Issue 内编写任何业务查询逻辑。

## Non-Goals

明确不做：

- **不实现 RBAC、OIDC、租户隔离过滤中间件**——AF-401（tenant 隔离过滤）、AF-402（OIDC）、AF-403（RBAC）是独立 Issue；本 Issue 用数据库约束保证"跨租户关联在物理上不可能被插入"，但不写任何"按当前请求租户自动过滤查询"的应用层中间件。
- **不实现真实的审批/审计业务 API**——AF-405（完整审计日志）、AF-305（durable 审批 Signal）是独立 Issue；本 Issue 只建表和约束，不写 `POST /approvals` 之类的路由或服务层代码。
- **不实现幂等账本（Idempotency Ledger）**——那是 AF-209/AF-307 的范畴，即使 `docs/02_ARCHITECTURE.md` 的 Idempotency Contract 提到 `run_id`/`step_id`，本 Issue 只是让这两个概念作为表存在，不建幂等专用表、不写幂等键唯一约束逻辑。
- **不实现 LangGraph Checkpoint（PostgresSaver）**——AF-303 的范畴；`runs`/`steps` 表描述的是 Temporal/业务层面的执行事实，不是 LangGraph 内部节点状态，两者在 State Ownership 上本来就不是同一个所有者（见 Relevant Documents）。
- **不定义任何具体 Agent（Intake/Clarifier/...）的业务字段**——`steps.name` 只是一个自由文本占位，AF-104-108 落地时如需要专属字段，应在各自 Design Note 中扩展迁移，不在本 Issue 里预建。
- **不接入用户/身份模型**——`approvals.decided_by`、`audit_events.actor` 在本 Issue 内是自由文本占位字段，不关联任何 `users` 表（AF-402/403 才会引入身份概念）。
- **不新增顶层模块包**——AF-101 已经把 `docs/02_ARCHITECTURE.md` 的六个顶层模块边界实现为真实 Python 包；本 Issue 的模型与迁移嵌套在既有的 `control_plane/` 包下，不引入第七个顶层包（见"包归属"一节，此前 Draft v1 提议新增 `domain/` 顶层包已被否决）。
- **不做数据库角色/权限分离**（例如给审计表单独一个只有 INSERT 权限的 DB 角色）——本 Issue 用触发器在应用共享的单一 DB 角色下强制约束，角色级别的最小权限收紧留给 AF-405/AF-407 一类的安全加固 Issue。

**修正**：本 Issue 的模型、会话工厂与迁移全部放进既有的 `control_plane/` 包下：

```text
alembic.ini               # 仓库根目录；Alembic CLI 的唯一入口
src/aegisflow_core/control_plane/
├── __init__.py          # 已存在（AF-101）
├── domain/
│   ├── __init__.py

│   ├── tenant.py
│   ├── workflow.py
│   ├── execution.py      # Run、Step（同属"执行事实"，放一个文件）
│   ├── approval.py
│   ├── audit.py
│   └── session.py        # 异步引擎/会话工厂
└── migrations/
    ├── env.py
    ├── script.py.mako
    └── versions/
        └── <timestamp>_initial_domain_model.py
```

根目录 `alembic.ini` 必须设置：

```ini
[alembic]
script_location = %(here)s/src/aegisflow_core/control_plane/migrations
```

`migrations/env.py` 必须显式导入 `tenant`、`workflow`、`execution`、`approval`、`audit` 五个模型模块，并把同一个 `Base.metadata` 设为 `target_metadata`，防止 Alembic 因模型未注册而静默漏表。AF-103 不创建 PostgreSQL `control_plane` schema；六张表、触发器函数与 Alembic version table 均使用默认 `public` schema。触发器函数使用带项目前缀的唯一名称 `aegisflow_prevent_workflow_mutation` 与 `aegisflow_prevent_audit_mutation`，避免把 Python 包名误当成数据库 schema。

迁移目录中的 `script.py.mako` 和 `versions/*.py` 属于运行迁移所需的部署资产。当前 Docker runtime 仅复制已安装虚拟环境、不复制源码或 `alembic.ini`，而本 Issue 不要求容器内执行迁移，因此不修改 Dockerfile；迁移由源码 checkout/CI 执行。未来若要求容器或发布 wheel 执行迁移，必须由独立 Issue 明确打包这些资产，不能假设它们已经存在于 runtime 镜像。

依据：`docs/02_ARCHITECTURE.md` 的 State Ownership 表把"Tenant、RBAC、版本、审批事实"统一归给 Core Domain/PostgreSQL 一个所有者，且 `control_plane/` 子包列表本来就包含 `tenants`/`approvals`/`audit`；`workflows`/`runs`/`steps` 虽然语义上更偏"执行事实"而非"治理"，但仍属于同一个 PostgreSQL 持久化事实来源，不属于 LangGraph 的 `runtime/state`（那是 Agent 内部节点状态，所有者不同）。放进 `control_plane/` 是在不新增架构面的前提下最接近正确的选择。

**遗留的软性问题（不阻塞本 Issue，供未来参考）**：如果后续某个包（例如 `evaluation/`）也需要自己的持久化表，届时"迁移文件要不要继续都放 `control_plane/migrations/`，还是该拆分/集中到别处"需要重新讨论，可能是那时候才需要 ADR 的架构决策。本 Issue 不预判这个问题的答案。

## Proposed Flow

### 1. 初始领域模型（六张表，含租户复合外键）

所有子表引用父表时，**外键包含 `tenant_id`**（复合外键指向父表的 `(tenant_id, id[, version])` 复合唯一约束），而不是只引用父表的 `id`——这样数据库会物理拒绝"A 租户的行引用 B 租户的父行"，把 R-006 跨租户泄露风险在写入路径上而不是查询路径上先堵一层。

| 表 | 关键列 | 约束 |
|---|---|---|
| `tenants` | `id`（UUID PK）、`slug`（非空）、`name`（非空）、`created_at` | `UNIQUE (slug)` |
| `workflows` | `id`（UUID PK）、`tenant_id`（FK→`tenants.id`，非空）、`name`（非空）、`version`（整数，非空）、`definition_hash`（文本，非空，占位）、`status`（`active`\|`superseded`，默认 `active`）、`created_at` | `UNIQUE (tenant_id, name, version)`；`UNIQUE (tenant_id, id, version)`（供 `runs` 复合外键引用）；触发器见"版本不可覆盖机制" |
| `runs` | `id`（UUID PK）、`tenant_id`（FK→`tenants.id`，非空）、`workflow_id`（非空）、`workflow_version`（整数，非空）、`status`（`pending`\|`running`\|`waiting_clarification`\|`waiting_approval`\|`completed`\|`failed`\|`cancelled`）、`created_at`、`updated_at` | `FOREIGN KEY (tenant_id, workflow_id, workflow_version) REFERENCES workflows (tenant_id, id, version)`——保证 `workflow_version` 永远精确对应一个真实存在的 Workflow 版本，不是无约束的冗余整数；`UNIQUE (tenant_id, id)`（供 `steps`/`approvals` 引用） |
| `steps` | `id`（UUID PK）、`tenant_id`（FK→`tenants.id`，非空）、`run_id`（非空）、`name`（文本，非空，占位）、`sequence`（整数，非空）、`status`（`pending`\|`running`\|`completed`\|`failed`\|`skipped`）、`created_at`、`completed_at`（可空） | `FOREIGN KEY (tenant_id, run_id) REFERENCES runs (tenant_id, id)`；`UNIQUE (run_id, sequence)`；`UNIQUE (tenant_id, run_id, id)`（供 step 级 `approvals` 引用） |
| `approvals` | `id`（UUID PK）、`tenant_id`（FK→`tenants.id`，非空）、`run_id`（非空）、`step_id`（可空）、`decision`（`pending`\|`approved`\|`rejected`）、`decided_by`（文本，可空）、`decided_at`（可空）、`reason`（可空）、`created_at` | `FOREIGN KEY (tenant_id, run_id) REFERENCES runs (tenant_id, id)`；`FOREIGN KEY (tenant_id, run_id, step_id) REFERENCES steps (tenant_id, run_id, id)`。`step_id IS NULL` 时后者按 PostgreSQL `MATCH SIMPLE` 不生效，允许 Run 级审批；非空时同时保证 Step 属于同一 Tenant 和同一 Run |
| `audit_events` | `id`（UUID PK）、`tenant_id`（FK→`tenants.id`，非空）、`actor`（非空，占位）、`action`（非空）、`resource_type`（非空）、`resource_id`（可空）、`decision`（可空）、`reason`（可空）、`trace_id`（可空）、`created_at`（非空） | 无 `updated_at`；触发器见"审计只追加机制" |

状态枚举一律用 `text` 列 + `CHECK` 约束实现，不使用 PostgreSQL 原生 `ENUM` 类型（原生枚举增删值需要特殊迁移操作，维护成本高于收益）；Python 侧模型可以用 `StrEnum` 做类型提示与应用层校验，但**最终护栏是数据库 `CHECK` 约束**，不是 Python 类型系统。

所有六张表的主键统一使用 PostgreSQL 原生 UUID 类型，以 `gen_random_uuid()` 作为数据库 `server_default`，不用自增整数——数据库是 ID 默认值的唯一所有者，原生 SQL 与 ORM 插入行为一致，也避免通过连续 ID 推断数据量或创建顺序。

全部时间字段统一使用 timezone-aware `TIMESTAMPTZ`；`created_at` 使用数据库端 `now()` 作为 `server_default`。`updated_at` 初始值同样由数据库生成，后续业务更新必须显式写入新值；AF-103 不额外引入自动更新时间触发器。

### 2. 版本不可覆盖机制（修正 Draft v1 的逻辑错误）

Draft v1 的触发器设计是"任何 `UPDATE` 一律拒绝"，但 `workflows.status` 字段本身就设计成 `active`\|`superseded` 两个值——这与"完全禁止 UPDATE"自相矛盾，会导致 `status` 永远无法从 `active` 变成 `superseded`。修正为**列级 + 状态迁移感知**的触发器逻辑：

```text
FUNCTION public.aegisflow_prevent_workflow_mutation():
  IF TG_OP = 'DELETE':
    RAISE EXCEPTION 'workflows rows cannot be deleted'

  # TG_OP = 'UPDATE'
  IF any of (id, tenant_id, name, version, definition_hash, created_at) changed:
    RAISE EXCEPTION 'workflows immutable columns cannot be modified'

  IF OLD.status = NEW.status:
    RETURN NEW   # 允许无操作的重复写入

  IF OLD.status = 'active' AND NEW.status = 'superseded':
    RETURN NEW   # 唯一允许的状态迁移

  RAISE EXCEPTION 'workflows.status can only transition from active to superseded'

TRIGGER: BEFORE UPDATE OR DELETE ON workflows FOR EACH ROW EXECUTE FUNCTION prevent_workflow_mutation()
```

即：`id`/`tenant_id`/`name`/`version`/`definition_hash`/`created_at` 永久不可变（这是 AC"版本不可覆盖"的核心含义）；`status` 只能单向流转 `active → superseded`，不能反向、不能跳到未定义值（`CHECK` 约束已经限制取值集合，触发器额外限制*迁移方向*）；行本身不可删除；需要"新版本"时只能 `INSERT` 一行新记录。

### 3. 审计只追加机制

`audit_events` 触发器函数 `public.aegisflow_prevent_audit_mutation`（`BEFORE UPDATE OR DELETE`）：无条件拒绝任何 `UPDATE` 或 `DELETE`（这张表没有类似 `status` 的合法可变字段，不需要 Draft v1 那种精细化处理，保持原设计）。角色级别的权限收紧（给审计写入一个只有 INSERT 权限的专用 DB 角色）留给后续安全加固 Issue。

### 4. Core 应用侧改动（最小）

- `settings.py` 新增 `database_url: str` 字段，`get_settings()` 校验 `DATABASE_URL` 环境变量存在且非空（不做连接字符串格式的深度校验，交给驱动层报错）。
- `control_plane/domain/session.py`：基于 SQLAlchemy 2.0 异步引擎（`create_async_engine`）+ `async_sessionmaker`，从 `settings.database_url` 构造；本 Issue **不**在 `app.py`/`create_app()` 里接入任何依赖注入或启动时自动建连——`/health` 契约保持 AF-101 锁定的浅层语义不变。

### 5. CI 迁移验证（新增，修正 Draft v1"仅本地验证"的决定）

审阅意见指出：AF-103 的核心交付物就是数据库迁移，只靠本地证据不足以满足"迁移测试通过"这条验收标准背后的"证据可独立验证"精神——这正是 CI-001 存在的意义。修正为：在 CI-001 已交付的 `.github/workflows/ci.yml` 的 `test` job 里新增一个 `postgres` service container，并在 `pytest` 步骤前后插入迁移验证：

```yaml
jobs:

    runs-on: ubuntu-24.04
    timeout-minutes: 15
    services:
      postgres:
        image: pgvector/pgvector:pg16@sha256:a36250871de0833b8757561c72f2477ef1ddd1101afa4e617fb552e0de514c6b
        env:
          POSTGRES_USER: aegisflow_ci
          POSTGRES_PASSWORD: aegisflow_ci
          POSTGRES_DB: aegisflow_ci
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U aegisflow_ci"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 10
    env:
      DATABASE_URL: postgresql+asyncpg://aegisflow_ci:aegisflow_ci@localhost:5432/aegisflow_ci
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1
        with:
          persist-credentials: false
      - uses: astral-sh/setup-uv@c771a70e6277c0a99b617c7a806ffedaca235ff9
        with:
          version: "0.11.31"
          python-version: "3.12"
          enable-cache: true
          cache-dependency-glob: uv.lock
      - run: uv sync --locked
      - run: uv run --locked alembic upgrade head
      - run: uv run --locked alembic upgrade head   # 幂等性检查：重复执行应为空操作
      - run: |
          uv run --locked python -m pytest \
            --cov=aegisflow_core \
            --cov-report=term-missing
      - run: uv run --locked alembic downgrade base
      - run: uv run --locked alembic upgrade head   # 验证降级后仍可再次升级
      - run: docker compose build core
```

`POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` 在此是 **CI job 生命周期内的一次性容器凭证**（job 结束容器即销毁，不持久、不对外可达、不授予任何真实资源的访问权限），不属于 `docs/09_SECURITY_BASELINE.md` 意义上的"真实 Secret"，因此直接写在 workflow 文件里而不是引用 `secrets.*`，这是 GitHub Actions service container 的标准做法，不违反 CI-001 已确立的"不引用 `secrets.*`"要求（那条要求针对的是真实凭证）。

上述镜像 digest 已于 2026-08-02 通过 registry manifest 元数据核验，对应 `pgvector/pgvector:pg16` 的 OCI index；CI 使用 digest 而不是可变 tag。迁移生命周期由 CI shell 步骤统一负责：pytest 假定 schema 已位于 `head`，只负责数据级测试，不在 fixture 中执行 upgrade/downgrade。pytest 数据隔离采用每测试事务回滚（预期约束异常在 nested transaction/savepoint 中断言）；不得用逐行 `DELETE` 清理 `workflows` 或 `audit_events`。CI 最后的 `downgrade base → upgrade head` 负责验证 DDL 回滚与重建，职责不与 pytest fixture 重叠。

## State Ownership

本 Issue 是 `docs/02_ARCHITECTURE.md` State Ownership 表中"Tenant、RBAC、版本、审批事实 → PostgreSQL"这一行第一次被真正实现。不涉及 Temporal Event History、LangGraph PostgresSaver、Redis Streams——那些所有者边界保持不变，本 Issue 不跨界。

## External Side Effects

有：迁移会对目标 PostgreSQL 数据库执行真实 DDL（建表、建约束、建触发器）。本地是 AF-102 的 `postgres` 容器，CI 中是 workflow 内的一次性 service container，均不触及任何生产资源，不需要幂等设计（Alembic 迁移天然基于版本号线性推进，重复执行 `alembic upgrade head` 是安全的空操作，已在 CI 步骤中显式验证）。

## Idempotency

不适用于本 Issue 范围内的表结构本身（幂等账本是 AF-209/307）。Alembic 迁移操作本身具备幂等性，已在 CI 中作为显式验证步骤。

## Failure Modes

| 失败场景 | 预期行为 |
|---|---|
| `DATABASE_URL` 缺失或为空 | `get_settings()` 抛出 `ConfigurationError`，与 `APP_ENV` 校验行为一致 |
| 迁移在空库上执行 | `alembic upgrade head` 成功建出全部六张表、约束、触发器 |
| 迁移重复执行 | `alembic upgrade head` 是空操作，不报错（CI 中显式验证） |
| 尝试修改 `workflows` 不可变列，或非法状态迁移 | 触发器抛出异常，事务回滚 |
| `workflows.status` 从 `active` 改为 `superseded` | 触发器放行，更新成功 |
| 尝试 `DELETE workflows` 已存在的行 | 触发器抛出异常 |
| 尝试 `UPDATE`/`DELETE` `audit_events` 已存在的行 | 触发器抛出异常 |
| 插入 `tenant_id` 与父行不一致的子表记录（跨租户关联） | 数据库层面因复合外键约束拒绝，抛出外键约束错误 |
| 插入 `workflow_version` 与 `workflow_id` 实际版本不符的 `run` | 数据库层面因复合外键约束拒绝 |
| 插入重复 `(tenant_id, name, version)` 的 `workflows` 行 | 数据库层面拒绝，抛出唯一约束错误 |

## Security Impact

- Risk Level：**L2**（`docs/09_SECURITY_BASELINE.md`）——涉及数据库 Schema 变更与 CI workflow 扩展，但仍在本地开发数据库与 CI 一次性容器上操作，无生产资源、无真实租户数据。
- 直接响应 `docs/13_RISK_REGISTER.md` R-006（Cross-tenant leak）：全部子表通过租户复合外键引用父表，数据库物理拒绝跨租户关联——这比"只有 `tenant_id` 列但不约束一致性"更强，但**仍不等于关闭 R-006**（真正的请求级隔离过滤是 AF-401 的范畴），PR 中不得声称"跨租户隔离已完成"。
- `workflows`/`audit_events` 的触发器是"确定性护栏优先于应用自觉"这条工程原则的直接体现。
- CI 新增的 `postgres` service container 凭证是一次性、无持久价值的 CI 内部凭证，不是真实 Secret（见"CI 迁移验证"一节说明）。
- 供应链：新增 SQLAlchemy、asyncpg、Alembic 三个 Python 依赖（Resolved Decisions 1），均是维护活跃、被广泛审计的主流库。

## Rollback

- Alembic 支持 `alembic downgrade base`；CI 已把"降级后能否再次升级"纳入自动验证。
- `git revert` PR 本身会移除迁移文件和触发器定义，但**不会**自动对已经执行过迁移的目标数据库做 `downgrade`——回滚代码和回滚数据库 schema 是两个独立动作，Rollback 步骤必须显式包含"如目标环境已跑过本迁移，需额外执行一次 `alembic downgrade`"。

## Resolved Decisions（v3：已吸收两轮人工审阅意见）

1. **ORM/迁移工具**：**SQLAlchemy 2.0（async）+ Alembic**（沿用 v1 建议，人工已批准）。依赖在 `pyproject.toml` 使用兼容版本范围，由 `uv.lock` 锁定精确版本。
2. ~~新增顶层 `domain/` 包~~ **已否决**，改为 `control_plane/domain/` + `control_plane/migrations/`，理由见"包归属"一节。
3. **状态枚举实现**：`text` 列 + 命名 `CHECK` 约束，不用 PostgreSQL 原生 `ENUM`（人工已批准）。
4. **模型文件组织**：按聚合拆分（`base.py`/`tenant.py`/`workflow.py`/`execution.py`/`approval.py`/`audit.py`），不用单一巨大 `models.py`（人工已批准，采纳审阅意见的具体文件划分）。
5. ~~迁移测试仅本地验证~~ **已否决**，改为直接扩展 CI-001 的 `test` job，新增 PostgreSQL service container，把 `alembic upgrade head` → 幂等重复 → 约束/触发器 pytest → `alembic downgrade base` → 再次 `upgrade head` → 完整 pytest 回归全部纳入 CI 自动验证（见"CI 迁移验证"一节）。
6. **Workflow 触发器范围**：**禁止 DELETE**（人工已批准，扩大 v1 范围）；**不是简单禁止所有 UPDATE**，而是禁止修改不可变列、只允许 `status` 从 `active` 单向流转到 `superseded`（修正 v1 的逻辑错误，见"版本不可覆盖机制"）。
7. **Approval/Step/Run 一致性**：step 级审批使用 `(tenant_id, run_id, step_id)` 三元复合外键；Run 级审批的 `step_id` 保持可空。
8. **Alembic/Schema**：根目录 `alembic.ini` 是唯一 CLI 入口；`env.py` 显式汇总全部模型 metadata；数据库对象使用 `public` schema，不创建名为 `control_plane` 的数据库 schema。
9. **测试隔离**：pytest 使用事务 rollback/savepoint，不使用逐行 DELETE；迁移 up/down 生命周期仅由 CI shell 和本地显式命令负责。
10. **供应链与命令锁定**：CI pgvector 服务使用已核验的 immutable digest；全部 Alembic 命令通过 `uv run --locked` 执行。
11. **数据库默认值**：UUID 使用 `gen_random_uuid()` server default；时间字段统一为 `TIMESTAMPTZ` + `now()` server default。
