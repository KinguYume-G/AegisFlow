# Design Note — AF-206 Implement Reviewer Agent contract

> 状态：**Draft v2**，等待人工最终 Review。依赖 AF-205（Draft，先于本 Issue 批准）。Codex 在获得批准前不得实现。v2 行为以共享契约 §0A 为准。
> 前提文档：`docs/design-notes/M2-SHARED-CONTRACTS.md`（第 8.4、8.5、4.3、12、13 节）。GitHub #25。`09_SECURITY_BASELINE.md` Risk Levels。

## Draft v2 implementation contract

- `ReviewDecision` 使用显式 `approval_status`，pending 时没有终态 outcome；approved/rejected 后生成对应 outcome，模型始终满足自身 validator。
- Draft PR 是 L3，因此执行成功后的 Reviewer 路径统一进入 pending approval；测试失败直接 rework，不进入审批。
- `ApprovalGateway` 全异步；协议与 InMemory fake 位于 DeliveryPack，Postgres adapter 位于 `control_plane`。
- migration `0004` 增加 `(tenant_id, run_id, step_id)` 唯一约束和数据库状态转换保护，只允许 `pending → approved|rejected`。

## Problem

Executor 产出的 Patch/Test/Evidence 需要被汇总成 Decision/Findings/Approval Need；高风险（L3）改动必须真正等待人工审批，而不是自动放行；审批等待还必须对 LangGraph 节点 replay 安全（镜像 AF-108 Clarifier HITL 已解决的问题）。

## Objective

按 Issue #25 AC（"输出 Decision、Findings、Approval Need；引用可追踪"），实现 `ReviewerAgent.review()`/`resolve()` 与 `ApprovalGateway`（`InMemoryApprovalGateway` + `PostgresApprovalGateway`）。

## Non-Goals

- 不做 Draft PR 创建（AF-208 职责）。
- 不做 LangGraph `interrupt()`/`Command(resume=...)` 编排（图节点职责，AF-210）。
- 不引入真实 LLM（`review()` 是确定性规则，不是模型判断——见 Proposed Flow，这与"Reviewer 是六个 Agent 之一"并不矛盾：M1 的 Planner/Clarifier 同样用确定性 Reasoner 实现了"Agent"契约）。
- 不做 Temporal Durable Signal（`PostgresApprovalGateway` 持久化的是**事实**，不是**等待机制**本身，等待机制仍是 M2 阶段的 LangGraph `interrupt()`，是 M3 AF-304/305 的替换目标）。

## Affected Modules

- 新增 `packs/delivery/contracts/review_decision.py`（`ReviewFinding`/`ReviewDecision`）。
- 新增 `packs/delivery/reviewer/` 下的纯协议、Reviewer 与 InMemory fake；PostgreSQL adapter 单独放在 `control_plane/approvals.py`，禁止 DeliveryPack 导入 SQLAlchemy。
- 新增 `tests/packs/delivery/reviewer/`。
- 修改 `runtime/tracing.py`：`StepTraceRecord.agent` 的 `Literal` 追加 `"reviewer"`（单行改动，AF-205 已追加 `"executor"`，本 Issue 在其基础上再追加一项）。
- 修改 `docs/21_TRACEABILITY_MATRIX.md`。

## Proposed Flow

### `ReviewDecision`（`packs/delivery/contracts/review_decision.py`）

```text
class ReviewFinding(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)
    schema_version: Literal[1] = 1
    severity: Literal["info", "warning", "blocking"]
    message: str

class ReviewDecision(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)
    schema_version: Literal[1] = 1
    findings: list[ReviewFinding]
    approval_status: Literal["not_required", "pending", "approved", "rejected"]
    outcome: Literal["draft_pr", "rework", "rejected"] | None = None
    reasoner_id: str

    @model_validator(mode="after")
    def state_is_consistent(self) -> "ReviewDecision":
        if self.approval_status == "pending" and self.outcome is not None:
            raise ValueError("outcome must be None while an approval decision is pending")
        if self.approval_status != "pending" and self.outcome is None:
            raise ValueError("terminal/non-required decisions require an outcome")
        return self
```

### `ReviewerAgent.review()`（固定顺序规则，镜像 Policy Gate/Clarifier 的写法）

```text
class ReviewerAgent:
    def __init__(self, reasoner: ReviewReasoner): ...

    def review(self, plan: Plan, execution_result: ExecutionResult) -> ReviewDecision:
        if execution_result.status == "failed":
            return ReviewDecision(
                findings=[ReviewFinding(severity="blocking", message="execution failed: tests did not pass")],
                approval_status="not_required", outcome="rework", reasoner_id=self._reasoner_id,
            )
        return ReviewDecision(
            findings=self._reasoner.summarize(plan, execution_result),
            approval_status="pending", outcome=None, reasoner_id=self._reasoner_id,
        )
```

规则顺序**固定**：先检查执行是否失败（失败直接打回，不进入审批队列——测试都没通过的改动不该消耗人工审批资源），再检查风险等级。`ReviewReasoner.summarize()` 是确定性摘要生成（例如把 `changed_files` 数量、`test_outcome` 统计信息组织成 `ReviewFinding` 列表），不是自由判断。

### `ReviewerAgent.resolve()`

```text
    def resolve(self, decision: ReviewDecision, approval: ApprovalOutcome) -> ReviewDecision:
        if decision.approval_status != "pending" or decision.outcome is not None:
            raise ValueError("resolve() only applies to a decision awaiting approval")
        if approval.decision == "approved":
            outcome = "draft_pr"
        elif approval.decision == "rejected":
            outcome = "rejected"
        else:
            raise InvalidApprovalDecisionError(approval.decision)
        resolved_status = "approved" if approval.decision == "approved" else "rejected"
        return ReviewDecision.model_validate(
            decision.model_dump() | {"approval_status": resolved_status, "outcome": outcome}
        )
```

### `ApprovalGateway`（`approval_gateway.py`）

AF-206 migration `0004` 增加 `(tenant_id, run_id, step_id)` 唯一约束和状态转换触发器；数据库只允许 `pending → approved|rejected`，应用层和数据库共同拒绝终态覆盖。

## State Ownership / External Side Effects / Idempotency

- **State Ownership**：`approvals` 表行的写入方是 `PostgresApprovalGateway`（AF-103 定义表结构，本 Issue 是第一个真正使用它的调用方，见 SHARED-CONTRACTS §4.3）。
- **External Side Effects**：`PostgresApprovalGateway` 写 PostgreSQL；无 GitHub 调用。
- **Idempotency**：`request_approval` 按 `(run_id, step_id)` 幂等（与 AF-108 `(run_id, step_key)` 同一动机：LangGraph 节点 replay 安全）；`submit_decision` 刻意非幂等（重复提交被拒绝，与 AF-108 `submit_response` 的"提交回复不能重试"语义一致）。

## Failure Modes

| 场景 | 预期行为 |
|---|---|
| Execution 失败 | `outcome="rework"`，`approval_status="not_required"` |
| 任意风险等级且测试通过 | `approval_status="pending"`，等待 `resolve()` |
| `resolve()` 在非等待状态下被调用 | `ValueError` |
| `approval.decision` 既非 `approved` 也非 `rejected` | `InvalidApprovalDecisionError`，不静默兜底 |
| `submit_decision` 对已终态的 approval 再次调用 | `DuplicateApprovalDecisionError`，原决定不被覆盖 |
| `submit_decision` 的 `run_id` 与存储记录不一致 | `ApprovalRunMismatchError`（镜像 AF-108 `ClarificationRunMismatchError`） |

## Security Impact

Risk Level L2（Reviewer 自身评估）；Create Draft PR 固定为 L3，因此成功执行统一进入 `approval_status="pending"`。审批事实写入 PostgreSQL，并由数据库约束保护终态。
