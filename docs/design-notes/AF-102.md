# Design Note — AF-102 Create Docker Compose foundation

> 状态：Approved。2026-08-02 由 Project Owner 批准 Design Note、Test Plan 与九项修正。
> 实现边界：仅本地开发容器基础；不修改应用代码，不引入 CI，不开始 AF-103。

## Problem

AF-101 已交付并合并（PR #77，`status:verified`）：`aegisflow_core` 六个模块边界包已存在，`create_app()` 可构造出最小 FastAPI 应用，`GET /health` 契约已锁定为 `{"status": "ok", "service": "aegisflow-core"}`，依赖用 `uv` 管理（`pyproject.toml` + `uv.lock`），Python 锁定 `>=3.12,<3.13`。但目前仓库里没有任何容器编排文件——Core 只能靠人工手动 `uv run uvicorn ...` 启动，没有 PostgreSQL、没有 Redis，M1 后续 Issue（AF-103 领域模型/迁移需要真实 PostgreSQL；未来 Redis Streams 相关能力需要真实 Redis）都缺少可用的本地依赖基础。

## Objective

按 `docs/05_GITHUB_ISSUE_BACKLOG.md` 中 AF-102 的原始 Acceptance Criteria："一条命令启动；healthcheck 通过；配置来自占位符"，建立：

1. 一个可以把 Core 打包成容器镜像的最小 `Dockerfile`；
2. 一个用 `docker compose` 把 Core、PostgreSQL、Redis 三个服务一条命令拉起的根目录 `compose.yaml`；
3. 三个服务各自的 Docker 原生 healthcheck，且 Core 的 healthcheck 直接复用 AF-101 已锁定的 `/health` 契约，不新增或修改该契约；
4. 补全 `.env.example` 中 PostgreSQL/Redis 容器自身引导所需的占位符字段（区别于 App 侧已有的 `DATABASE_URL`/`REDIS_URL`）。

## Non-Goals

明确不做（越界即为范围外，需拆到对应后续 Issue）：

- **不给 Core 应用代码接入真实的 PostgreSQL/Redis 客户端或连接逻辑**——`aegisflow_core/settings.py` 目前不读取 `DATABASE_URL`/`REDIS_URL`（AF-101 Design Note 已明确留白），本 Issue 同样不新增读取；真正的数据库连接、连接池、ORM/迁移属于 AF-103（领域模型与迁移）。
- **不新增 `GET /health/ready` 或任何"深度健康检查"端点**——AF-101 Design Note 提到 AF-102 阶段"可能"新增该端点，本设计评估后认为不需要：Docker Compose 的 healthcheck 完全可以由 postgres/redis 各自的原生探活 + Core 复用既有 `/health` 组成，不必现在扩大应用层契约面。若未来确有"Core 是否能连上 DB"的探活需求，应作为独立 Issue（伴随真实 DB 客户端一起）处理，不在本 Issue 内提前占位。
- **不使用 pgvector 扩展、不建表、不跑迁移**——见"关键设计决策 1"，本 Issue 只在镜像选型上为未来免一次重建做准备，不代表 pgvector 功能在本 Issue 内被使用或验证。
- **不接入 Temporal**——`docs/06_DEVELOPER_GUIDE.md` 的预期工具链提到 Temporal，但 AF-102 的 Objective 原文只提 Core/PostgreSQL/Redis；Temporal 属于 AF-301（Bootstrap Temporal workflow and worker），不在本 Issue 范围。
- **不是 AF-204（Docker 沙箱基线）**——AF-204 是 Executor Agent 用来跑不可信代码/测试的安全隔离沙箱（non-root、no Docker socket、resource limit、network disabled/allowlist，`docs/09_SECURITY_BASELINE.md` Sandbox 一节）；AF-102 的 `compose.yaml` 只是开发者本机运行 Core 自身及其直接依赖的编排文件，两者共享"Docker"这个技术但解决完全不同的问题，本 Issue 不得与 AF-204 的沙箱需求混淆或提前实现。
- **不配置生产/演示部署**——`docs/adr/0004-no-terraform.md` 与 `docs/02_ARCHITECTURE.md` Deployment Evolution 明确 Demo 用 k3s + Helm（AF-512/513），Docker Compose 仅用于 Development。
- **不引入 CI**——沿用 AF-101 已批准的决定（CI 不纳入骨架类 Issue，留待独立 Issue）。
- **不新增 Makefile / lint / typecheck 工具链**——同样沿用 AF-101 的既有排除范围，除非本 Issue 被人工明确扩大。

## Proposed Flow

### 1. 服务拓扑

```text
docker compose up
        │
        ├── postgres  (pgvector/pgvector:pg16，见决策 1)
        │      healthcheck: pg_isready
        │      volume: postgres_data:/var/lib/postgresql/data（本地持久化，非生产）
        │
        ├── redis     (redis:7-alpine)
        │      healthcheck: redis-cli ping
        │
        └── core      (本仓库 Dockerfile 构建)
               depends_on: postgres(healthy), redis(healthy)   # 仅编排顺序，不代表 core 已连接
               healthcheck: 复用 GET /health（AF-101 契约，见决策 3）
               ports: 127.0.0.1:8000:8000
```

`depends_on` 的 `service_healthy` 条件只保证 **启动顺序**（Core 容器在 postgres/redis 健康后才启动），**不代表** Core 应用真的去连接了它们——这与 Non-Goals 中"不接入真实客户端"完全一致：AF-102 只是把三个独立服务摆到同一个 Compose 网络里，各自独立健康，互不耦合业务逻辑。

### 2. `Dockerfile`（Core）设计

多阶段构建，基于 `python:3.12-slim`（与 AF-101 锁定的 `>=3.12,<3.13` 一致）：

```text
FROM ghcr.io/astral-sh/uv:0.11.31@sha256:ecd4de2f060c64bea0ff8ecb182ddf46ba3fcccdc8a60cfdbaf20d1a047d7437 AS uv
FROM python:3.12-slim@sha256:57cd7c3a7a273101a6485ba99423ee568157882804b1124b4dd04266317710de AS builder
COPY --from=uv /uv /uvx /bin/
WORKDIR /app
COPY pyproject.toml uv.lock README.md ./
RUN uv sync --locked --no-dev --no-install-project
COPY src/ ./src/
RUN uv sync --locked --no-dev --no-editable
FROM python:3.12-slim@sha256:57cd7c3a7a273101a6485ba99423ee568157882804b1124b4dd04266317710de AS runtime
COPY --from=builder /app/.venv /app/.venv
USER appuser
EXPOSE 8000
CMD ["uvicorn", "aegisflow_core.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

要点：

- `uv sync --locked`：严格按 `uv.lock` 安装；`uv` 只存在于 builder，runtime 不执行 `uv sync` 或 `uv run`。
- 分两步 `uv sync`（先不带项目本身装依赖、再连项目一起装）是为了让 Docker layer cache 在只改 `src/` 代码时不必重装全部依赖，纯粹是构建速度优化，不影响行为。
- **非 root 用户**运行（`appuser`）——不是 AF-204 的沙箱要求，是通用容器安全最佳实践，独立成立。
- `.dockerignore` 排除 `.git/`、`.venv/`、`__pycache__/`、`tests/`、`docs/`、`archive/`、`*.md`、`.env`（防止本地真实 `.env`——如果开发者已自行创建——被意外 `COPY` 进镜像）。

### 3. `compose.yaml` 设计

- 不写 `version:` 键（Compose V2 已不需要，写了反而是过时噪音）。
- 三个服务的容器名、网络使用 Compose 默认命名（不显式指定 `container_name`，避免多个开发者本机同时起多套环境时命名冲突）。
- Postgres/Redis 端口按决策 5 绑定到 `127.0.0.1`，不绑定 `0.0.0.0`，降低本机被局域网访问的意外暴露面（与 `docs/09_SECURITY_BASELINE.md` 默认策略的"最小暴露"精神一致，即使这不是生产环境）。
- 不用 `env_file` 把整个 `.env` 注入服务。Core 只接收 `APP_ENV`、`APP_BASE_URL`；Postgres 只接收三个 bootstrap 变量；Redis 不接收环境变量。
- 必需变量使用 `${VAR:?message}` 在配置渲染阶段 fail-fast；宿主端口可由 `CORE_HOST_PORT`、`POSTGRES_HOST_PORT`、`REDIS_HOST_PORT` 调整，容器内 Core 端口固定为 `8000`。
- 卷：只给 `postgres` 建命名卷 `postgres_data` 做持久化；`redis` 不加持久化卷（Streams 场景下开发期数据丢失可接受，简化配置）。

### 4. Core 健康检查怎么接（不新增应用代码）

Docker healthcheck 指令直接对已运行的 Core 容器发起自检：

```text
healthcheck:
  test: ["CMD", "python", "-c", "import urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://localhost:8000/health', timeout=2).status == 200 else 1)"]
  interval: 5s
  timeout: 3s
  retries: 5
  start_period: 5s
```

用 Python 标准库单行脚本而不是 `curl`（见决策 4），避免仅为了 healthcheck 给运行时镜像多装一个系统包。这条 healthcheck 命中的正是 AF-101 已锁定、未被本 Issue 修改的 `/health` 契约——是本 Issue 对 AF-101 契约"消费方"身份的直接体现，而不是重新定义健康检查语义。

### 5. `.env.example` 新增字段

在现有 `DATABASE_URL`/`REDIS_URL` 基础上，新增 Postgres/Redis 容器自举所需的**离散**字段（官方镜像的环境变量约定，不接受完整连接串）：

```env
# Docker Compose — PostgreSQL container bootstrap (used by the postgres service itself)
POSTGRES_USER=<POSTGRES_USER>
POSTGRES_PASSWORD=<POSTGRES_PASSWORD>
POSTGRES_DB=<POSTGRES_DB>
POSTGRES_HOST_PORT=<POSTGRES_HOST_PORT>

# Docker Compose — Redis container bootstrap
REDIS_HOST_PORT=<REDIS_HOST_PORT>
```

这些字段与已存在的 `DATABASE_URL`/`REDIS_URL` 存在信息重复（开发者需要保证两边手填的值一致，例如 `DATABASE_URL` 里的用户名密码要和 `POSTGRES_USER`/`POSTGRES_PASSWORD` 对得上）——这是官方 Postgres/Redis 镜像的固有限制（它们不解析连接串）。Project Owner 已批准接受该冗余，保持 `compose.yaml` 简单可读。

按 `docs/06_DEVELOPER_GUIDE.md`"测试数据库与开发数据库分离"的原则，`POSTGRES_DB` 的占位符命名应提示这是开发库（例如未来真实值建议为 `aegisflow_dev`），但 `.env.example` 本身仍只放 `<POSTGRES_DB>` 占位符，不建议具体名字进代码库。

## State Ownership

不适用。本 Issue 不引入任何应用状态读写；`postgres`/`redis` 容器此刻只是空跑的基础设施，没有被任何业务代码使用，`docs/02_ARCHITECTURE.md` 的 State Ownership 表仍待 AF-103+ 才真正生效。

## External Side Effects

无。`docker compose up` 只在开发者本机创建容器和本地命名卷，不产生任何跨进程/跨网络的外部副作用，无需幂等设计。（注意与"外部系统副作用"区分：这不是 AF-207/AF-307 讨论的那类需要 Idempotency Ledger 的副作用。）

## Idempotency

不适用（无外部副作用）。`docker compose up` 本身对已运行的服务是幂等的（重复执行不会创建重复容器），这是 Docker Compose 工具自身的行为，不需要本 Issue 额外设计。

## Failure Modes

| 失败场景 | 预期行为 |
|---|---|
| `.env` 文件不存在或必需变量为空 | `${VAR:?message}` 使 `docker compose config` 在创建任何容器前返回非 0，并指出具体缺失变量 |
| Postgres/Redis 容器健康检查未通过 | Core 容器因 `depends_on: condition: service_healthy` 而不会启动，`docker compose ps` 明确显示 postgres/redis 处于 unhealthy，问题定位在依赖层，不会误导到 Core 代码 |
| Core 镜像构建失败（`uv sync --locked` 因 `uv.lock` 与 `pyproject.toml` 不一致而报错） | 构建阶段直接失败，不产出可运行镜像；这是刻意设计（避免依赖漂移被悄悄放行） |
| 端口冲突（开发者本机已有服务占用 8000/5432/6379） | `docker compose up` 报端口绑定失败；开发者通过三个 `*_HOST_PORT` 变量调整宿主端口，不修改容器内端口 |

## Security Impact

- Risk Level：**L1/L2**（`docs/09_SECURITY_BASELINE.md`）——本机开发环境编排，无生产部署、无外部网络暴露（端口绑定 `127.0.0.1`）、无真实 Secret。
- `.env.example` 新增字段全部为占位符，符合 AF-007 已建立的契约；不提供任何默认生产密码（`docs/14_CONFIGURATION_REFERENCE.md` 原则）。
- Postgres/Redis 端口只绑定本机回环地址，不绑定 `0.0.0.0`，降低同网络其他主机意外访问的风险。
- Core 容器以非 root 用户运行（`appuser`），符合最小权限精神，但**这不是** AF-204 要求的安全沙箱，不得在文档或 PR 描述中把两者混为一谈。
- 供应链：`uv`、Python、pgvector/PostgreSQL、Redis 均同时固定版本 tag 与不可变多架构 digest，不使用 `latest`。

## Rollback

- 无数据库迁移、无生产资源、无真实 Secret——回滚即 `git revert` 对应 PR 合并 commit；本机执行 `docker compose down -v` 清理容器与卷即可完全复原，无残留外部状态。
- 因为 AF-103（领域模型/迁移）会直接依赖本 Issue 提供的 `postgres` 服务（甚至可能依赖决策 1 的 pgvector 镜像选型），若本 Issue 合并后需要回滚，需先确认 AF-103 是否已在此基础上开始实现。

## 已批准的关键设计决策

1. Postgres 使用 `pgvector/pgvector:pg16`，本 Issue 不启用扩展、不建表、不迁移。
2. `Dockerfile` 与现代 Compose Specification 文件 `compose.yaml` 均放仓库根目录。
3. 使用 `uv:0.11.31`，仅在 builder 中解析锁文件；runtime 只复制虚拟环境，不运行 `uv sync`。
4. Core healthcheck 使用 Python 标准库并精确验证 AF-101 `/health` 契约，不安装 `curl`。
5. 三个服务的宿主端口都只绑定 `127.0.0.1`。
6. 接受 bootstrap 字段与 URL 的必要冗余，但对每个服务使用显式环境变量 allowlist，不整体注入 `.env`。
7. Core 容器内端口固定 `8000`，宿主端口由 `CORE_HOST_PORT` 配置。
8. `APP_ENV` 与 PostgreSQL bootstrap 字段使用 `${VAR:?message}`，缺失时在 Compose 配置阶段失败。
9. 所有外部基础镜像同时固定版本与 digest。
