# Design Note — AF-209 Implement webhook and tool-call idempotency

> 状态：**Draft v2**，等待人工最终 Review。依赖 AF-201、AF-208（均为 Draft，先于本 Issue 批准）。Codex 在获得批准前不得实现。v2 行为以共享契约 §0A 为准。
> 前提文档：`docs/design-notes/M2-SHARED-CONTRACTS.md`（第 11、13 节）。GitHub #28。`18_RELIABILITY_PLAN.md`。

## Draft v2 implementation contract

- migration 使用 `0005`；记录显式保存 tenant/scope/canonical key/arguments hash/attempt token/lease expiry/result。
- `begin()` 返回 `Execute(claim_token) | Reuse(result) | InProgress | FinalFailure`，不得用 `None` 混合表示“未命中”和“正在执行”。
- `complete()`/`fail()` 必须带 claim token 条件更新；过期 lease 才能由新 attempt 接管，旧执行者不能覆盖新结果。
- AF-201 webhook dispatch 必须接入该 Ledger；相同 delivery 的并发与跨重启重放不得产生第二次 Gate 1B 执行。

## Problem

AF-201 阶段的 Webhook 防重放只做窗口级审计标记，不做精确一次处理；AF-208 阶段的 Draft PR 幂等只依赖远端 Marker 搜索，存在 TOCTOU 竞态窗口。两者都需要一个持久化的、唯一约束保护的本地 Ledger 才能达到 M2 Exit 标准（"重复 Webhook 不重复建 PR"）。

## Objective

按 Issue #28 AC（"唯一键含 tenant/run/step/tool/args hash；重复 PR 数 0"），实现 `idempotency_records` 表与 `IdempotencyLedger` 服务，并提供：

1. `PostgresIdempotencyGuard`（实现 AF-208 §10.0 定义的 `IdempotencyGuard` 协议）；
2. Webhook 精确一次处理的查询/写入接口（供 AF-210 图组装或未来 AF-201 升级路径调用）。

## Non-Goals

- 不修改 AF-201/AF-208 已冻结的文件本身（通过 §10.0 的注入缝 / 独立查询接口集成，不回头编辑）。
- 不实现 Temporal Saga/补偿工作流（`COMPENSATED` 状态在本 Issue 内只是一个可写入的终态标记，不实现自动补偿动作触发器——那是 M3 范围）。
- 不做跨请求分布式锁以外的并发控制（唯一约束是本 Issue 唯一的并发保护机制）。
- 不引入真实模型/GitHub 调用。

## Proposed Flow

### `IdempotencyRecord`（`control_plane/domain/idempotency.py`）

```text
class IdempotencyRecord(UUIDPrimaryKeyMixin, CreatedAtMixin, Base):
    __tablename__ = "idempotency_records"
    __table_args__ = (
        UniqueConstraint("idempotency_key", name="uq_idempotency_records_key"),
        CheckConstraint(
            "status IN ('pending','executing','succeeded','failed_retryable','failed_final','compensated')",
            name="status",
        ),
        CheckConstraint("scope IN ('webhook_delivery','tool_call')", name="scope"),
    )
    scope: Mapped[str]
    idempotency_key: Mapped[str]
    tenant_id: Mapped[UUID]        # ForeignKey("tenants.id", ondelete="RESTRICT")
    run_id: Mapped[UUID | None]
    step_id: Mapped[UUID | None]
    tool_name: Mapped[str | None]
    status: Mapped[str]
    result_reference: Mapped[str | None]
    updated_at: Mapped[datetime]
```

迁移 `0005_add_idempotency_ledger.py`：`0004` 已由 AF-206 审批约束占用；本迁移建 Ledger 表，`downgrade()` 删表。

### `IdempotencyLedger`（`control_plane/idempotency_ledger.py`）

```text
class IdempotencyLedger:
    def __init__(self, session_factory: Callable[[], AsyncSession], clock: Clock): ...

    async def begin(
        self, *, scope: Literal["webhook_delivery", "tool_call"], idempotency_key: str,
        tenant_id: UUID, arguments_hash: str, run_id: UUID | None,
        step_id: UUID | None, tool_name: str | None,
    ) -> Execute | Reuse | InProgress | FinalFailure:
        """单事务 claim。新 key 或过期 retryable lease 返回 Execute(new token)；
        succeeded 返回 Reuse；活跃 lease 返回 InProgress；final failure 返回 FinalFailure。"""
        ...

    async def complete(self, idempotency_key: str, *, claim_token: UUID, result_reference: str) -> None:
        """只有当前 claim token 可执行 EXECUTING → SUCCEEDED。"""
        ...

    async def fail(self, idempotency_key: str, *, claim_token: UUID, retryable: bool) -> None:
        """只有当前 claim token 可执行失败转换。"""
        ...
```

`begin()` 的 `INSERT ... ON CONFLICT DO NOTHING` + 回查是本 Issue 的核心并发原语（`18_RELIABILITY_PLAN.md`"唯一约束或锁保证一个执行者"）。

### `PostgresIdempotencyGuard`（`gateway/github/idempotency_guard.py`）

```text
class PostgresIdempotencyGuard:
    """以纯 async 方法实现 AF-208 IdempotencyGuard；不做事件循环桥接。"""
    async def begin(self, command: IdempotentCommand) -> ClaimResult: ...
    async def complete(self, claim_token: UUID, result_reference: str) -> None: ...
    async def fail(self, claim_token: UUID, retryable: bool, reason: str) -> None: ...
```

AF-208 已从首次实现起定义 async Guard，因此 AF-209 不做 `asyncio.run` 或同步桥接，也不需要后置修改前序协议。

## State Ownership / External Side Effects / Idempotency

- **State Ownership**：`idempotency_records` 是新的 Core Domain PostgreSQL 表，本 Issue 是唯一所有者。
- **External Side Effects**：不直接调用 GitHub；但必须把 AF-201 webhook 的 replay/dispatch adapter 切换为 Ledger，成功 claim 后才调用注入的 Gate 1B dispatcher。
- **Idempotency**：这正是本 Issue 存在的目的——`begin()`/`complete()`/`fail()` 三个方法共同构成幂等状态机的操作面。

## Failure Modes

| 场景 | 预期行为 |
|---|---|
| 并发 `begin()` 竞争同一 key | 恰好一个 `Execute`，其余为 `InProgress`/`Reuse` |
| 已 `SUCCEEDED` 的 key 再次 `begin()` | 返回 `Reuse(result_reference)` |
| `EXECUTING` 状态下进程崩溃（未调用 `complete`/`fail`） | **已知局限**：本 Issue 不实现超时自动回收 `EXECUTING`→`FAILED_RETRYABLE` 的清理机制（那需要一个后台任务或 Temporal Activity 超时，M3 范围）；记录为 Limitations,不在本 Issue 测试范围内担保 |
| `FAILED_FINAL` 的 key 再次 `begin()` | 返回 `FinalFailure`，不重试 |

## Security Impact

Risk Level L1（数据库读写，无外部副作用）。`19_THREAT_MODEL.md` 的 `Webhook Forgery/Replay` 与 `Partial Side Effect`（`18_RELIABILITY_PLAN.md` Failure Taxonomy）通过本 Issue 得到实质缓解——这是 M2 Exit 标准"重复 Webhook 不重复建 PR"的直接实现者。
